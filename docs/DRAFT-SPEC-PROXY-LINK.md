# PackageHub и прокси — этап Э0 «Связка»: черновик спецификации

> Черновик. Разворачивает этап Э0 из [вектора развития](./PRODUCT-VECTOR-2026-11.md) (раздел 5). Не принят к работе, не меняет действующие спецификации и не является источником поведения. Если этап возьмут в работу, документ переносится в корень как `SPEC-PROXY-LINK.md`, а изменения из раздела 11 вносятся в действующие спецификации тем же PR.

**Дата:** 2026-11-15
**Статус:** черновик; построен на допущениях о прокси (раздел 2), решения за владельцем — раздел 12
**Обозначения:** Э0 — этап вектора развития; не путать с этапом E0 мультиэкосистемной волны

## 0. Коротко

1. **Цель этапа — прокси и PackageHub видят друг друга.** Прокси по-прежнему решает сам и ничего не блокирует по-новому. PackageHub узнаёт, что прокси заблокировал и что через него скачивали.
2. **Пользователь получает две вещи:** на карточке и в API видно, заблокирована ли версия и почему; отказ прокси содержит ссылку на страницу с причиной.
3. **PackageHub читает данные у прокси сам** (выгрузка блокировок и журнала скачиваний). Прокси к PackageHub не обращается, поэтому простой PackageHub на раздачу пакетов не влияет.
4. **PackageHub впервые работает через прокси как через источник** для семи экосистем. Это самая дешёвая проверка главной непроверенной гипотезы оценки и первый пакет работ: ему не нужен новый контракт.
5. **Вердиктов, правил и бюллетеней на этом этапе нет.** Статус версии складывается только из фактов прокси. Отсутствие блокировки не означает одобрения.
6. **Черновик держится на девяти допущениях о прокси** (раздел 2). Три из них меняют устройство этапа; их стоит подтвердить до начала работ.

## 1. Цель и рамки

### 1.1 Что входит

| Что | Результат |
|---|---|
| Прокси как источник метаданных | каталог семи экосистем обновляется через прокси под учётной записью сервиса |
| Выгрузка блокировок | PackageHub знает действующие блокировки прокси и их причины, хранит историю |
| Выгрузка журнала скачиваний | PackageHub знает, какие версии запрашивали и какие запросы закончились отказом |
| Статус версии в API и на карточке | «заблокирована / не заблокирована», причина, была ли версия в контуре |
| Ссылка в отказе прокси | пользователь из отказа попадает на страницу с причиной |
| Измерение | охват каталога и исходные значения мер направления (вектор, раздел 8) |

### 1.2 Что не входит

- **Вердикт и политика.** PackageHub ничего не решает; правила, режимы и симуляция — этап Э1.
- **Бюллетени OSV** и сопоставление с версиями — Э1.
- **Проверка манифеста и замена, посчитанная через resolve** — Э1 и Э4. На Э0 есть только пакетный запрос статуса по списку purl (раздел 6.1): им уже можно проверить lock-файл скриптом.
- **Пользователи, роли, исключения** — Э2.
- **Автоматическое расширение каталога** скачанными пакетами. Решение D1 (курируемый каталог) на Э0 не меняется: охват только измеряется.
- **Уведомления.** Оповещает по-прежнему корпоративная система.

### 1.3 Готово, когда

1. Для любой версии, которую прокси отдал или в которой отказал, PackageHub показывает статус: и для пакетов каталога, и для пакетов вне его.
2. Отказ прокси по каждой обслуживаемой экосистеме содержит ссылку, и она открывает страницу с причиной.
3. Блокировка, поставленная на прокси, видна в PackageHub не позже чем через 10 минут; запись журнала — не позже чем через час.
4. Запросы самого PackageHub не попадают в учёт использования.
5. Остановка PackageHub не меняет поведение прокси (проверяется тестом на стенде).
6. Есть отчёт об охвате каталога за 30 дней и исходные значения мер из раздела 9.

## 2. Допущения о прокси

Факты о прокси известны только со слов владельца (оценка, раздел 1.1). Ниже то, что черновик принимает дополнительно. Жирным выделены допущения, которые меняют устройство этапа.

| № | Допущение | Если неверно |
|---|---|---|
| А1 | **Прокси — репозиторный прокси:** у каждой экосистемы свой адрес, протокол родной (как у Nexus), а не HTTP-прокси общего назначения | источники остаются публичными адресами, а HTTP-клиенту PackageHub задаётся прокси; раздел 4 упрощается, раздел 3 не меняется |
| А2 | **Прокси сам определяет пакет и версию запрошенного артефакта** (иначе он не мог бы блокировать по версии) | разбор имён файлов переносится в плагины PackageHub; это затрагивает контракт плагина (`backend/app/ecosystems/base.py`, защищённый путь) |
| А3 | **Список блокировок хранится на прокси** в виде, пригодном для выгрузки: цель, причина, дата | если блокировки приходят из корпоративной системы без причины и даты, на карточке будет только факт блокировки |
| А4 | Блокировка задаётся на пакет целиком, на перечень версий или на диапазон версий | для блокировок по файлу или по контрольной сумме добавляется вид цели `file` |
| А5 | Прокси ведёт журнал запросов артефактов с учётной записью и исходом и хранит его не меньше 30 дней | при меньшем сроке PackageHub читает чаще; при отсутствии журнала раздел 3.2 становится работой на стороне прокси |
| А6 | Запросы метаданных и запросы артефактов прокси различает | в выгрузку попадают все запросы, PackageHub отбрасывает метаданные по расширению и пути |
| А7 | Пользователь прокси опознаётся учётной записью (не только адресом) | исключение сервиса делается по адресу; поле `account` в выгрузке пустое |
| А8 | Прокси может пропустить запросы JSON API PyPI и API crates.io либо уже пропускает | PackageHub работает через `pypi-simple` и PEP 658; у крейтов нет описаний и лицензий (раздел 4.2) |
| А9 | Есть тестовый экземпляр прокси или возможность поднять его рядом со стендом | проверка идёт на эмуляторе выгрузки (раздел 8), а связка с настоящим прокси проверяется только в контуре |

## 3. Контракт «прокси → PackageHub»

### 3.0 Направление и транспорт

**Данные идут от прокси к PackageHub, запросы — от PackageHub к прокси.** Прокси отдаёт две выгрузки по HTTP, PackageHub читает их по расписанию под своей учётной записью.

Почему так, а не отправка событий со стороны прокси:

- прокси не зависит от доступности PackageHub: ни очереди, ни повторов, ни учётных данных PackageHub на его стороне;
- после простоя PackageHub дочитывает с сохранённой позиции, события не теряются;
- учётная запись на прокси сервису нужна в любом случае: через неё он читает метаданные.

Запасной вариант, если прокси не может отдавать выгрузку по HTTP: те же записи файлами NDJSON в общем каталоге. Формат записей тот же, меняется только способ чтения.

Обе выгрузки версионируются в пути (`/export/v1/…`). Добавление полей версию не меняет; PackageHub неизвестные поля игнорирует.

### 3.1 Блокировки: снимок состояния

`GET <прокси>/export/v1/blocks` возвращает **полный список действующих блокировок**. Разблокировка — исчезновение записи из снимка; историю (когда снята) ведёт PackageHub.

```json
{
  "revision": "2026-11-15T10:42:07Z-318",
  "generated_at": "2026-11-15T10:45:00Z",
  "blocks": [
    {
      "id": "b-1042",
      "ecosystem": "npm",
      "name": "@scope/pkg",
      "target": {"kind": "versions", "versions": ["4.17.20", "4.17.21"]},
      "reason_kind": "vulnerability",
      "reason": "Удалённое выполнение кода, исправлено в 4.17.22",
      "reference": "GHSA-xxxx-xxxx-xxxx",
      "blocked_at": "2026-11-14T08:00:00Z"
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `revision` | непрозрачная метка состояния; она же `ETag`. Запрос с `If-None-Match` получает 304, если список не менялся |
| `id` | устойчивый идентификатор блокировки на прокси |
| `ecosystem`, `name` | как их знает прокси; PackageHub нормализует имя правилами своей экосистемы |
| `target.kind` | `package` (все версии), `versions` (перечень) или `range` (ограничение в синтаксисе экосистемы, поле `range`) |
| `reason_kind` | `vulnerability`, `security_decision`, `other` |
| `reason` | текст **для пользователей**. Внутренние заметки службы безопасности в выгрузку не попадают (решение 2, раздел 12) |
| `reference` | идентификатор бюллетеня или обращения, если есть |
| `blocked_at` | когда блокировка поставлена |

- **Чтение.** Раз в 5 минут (настройка). Снимок применяется целиком в одной транзакции: новые записи добавляются, изменившиеся обновляются, исчезнувшие получают `lifted_at`.
- **Защита от пустого снимка.** Если снимок пуст или в нём исчезло больше половины действующих блокировок, он не применяется; в состоянии связки остаётся предупреждение, решение принимает администратор. Так сбой выгрузки не «разблокирует» всё на витрине.
- **Диапазоны** сопоставляются с версиями через `VersionScheme` экосистемы, как ограничения зависимостей. Диапазон, который не разбирается, сохраняется как есть и показывается текстом; версии под него не помечаются, запись попадает в счётчик отклонённых.
- **RPM.** Координаты, которых нет в имени (архитектура, репозиторий), передаются в `qualifiers`. Сопоставление с адресацией RPM в PackageHub уточняется, когда станет известно, как прокси блокирует RPM.

### 3.2 Скачивания: журнал с позицией

`GET <прокси>/export/v1/downloads?after=<позиция>&limit=<n>` возвращает записи **о запросах артефактов** по порядку.

```json
{
  "records": [
    {
      "seq": 9813377,
      "at": "2026-11-15T10:41:55Z",
      "ecosystem": "pypi",
      "name": "requests",
      "version": "2.31.0",
      "filename": "requests-2.31.0-py3-none-any.whl",
      "outcome": "served",
      "fetched": false,
      "block_id": null,
      "account": "u-48213",
      "account_kind": "user"
    }
  ],
  "next": "9813377",
  "more": false
}
```

| Поле | Смысл |
|---|---|
| `seq` | монотонный номер записи; позиция чтения. Доставка «не меньше одного раза», PackageHub идемпотентен по `seq` |
| `outcome` | `served` (отдан), `blocked` (отказ по блокировке), `not_found`, `upstream_error` |
| `fetched` | для `served`: артефакт в этот раз скачан из интернета, а не взят из кэша прокси |
| `block_id` | для `blocked`: какая блокировка сработала |
| `account`, `account_kind` | непрозрачный идентификатор и вид учётной записи: `user`, `ci`, `service`. На Э0 PackageHub эти поля не хранит (решение 1, раздел 12); они в контракте сразу, чтобы этап Э4 его не менял |

- **Запросы самого PackageHub** прокси в выгрузку не включает (раздел 4.3).
- **Чтение.** Раз в 10 минут, пачками, пока `more` истинно. Позиция сохраняется в той же транзакции, что и агрегаты.
- **Что хранит PackageHub.** Не сами записи, а агрегаты по версии: первое и последнее обращение, число выдач, число отказов. Журнал остаётся на прокси: он — система учёта «кто что скачал».
- **Что не разобрано.** Запись с именем или версией, которые экосистема не принимает, не останавливает чтение: она считается в метрике, а последние такие записи хранятся для разбора.

## 4. Прокси как источник метаданных

### 4.1 Подключение

Прокси подключается штатной моделью источников (SPEC-MULTI-ECOSYSTEM §6, §13): по источнику на экосистему, с протоколом этой экосистемы, и профиль по умолчанию, в котором этот источник единственный. Публичные источники в контуре выключаются. Описание — файл для `app.cli registries import`, как `backend/registries.example.yaml`.

Новых понятий не требуется: источник включается только после проверки соединения, секрет лежит вне базы (`credentials_ref`).

### 4.2 Что нужно от прокси по экосистемам

| Экосистема | Протокол источника | Что прокси должен отдавать | Если не отдаёт |
|---|---|---|---|
| PyPI | `pypi-warehouse` | Simple API и JSON API `/pypi/<имя>/json` | `pypi-simple`: нет описаний и лицензий; зависимости только через файлы `.metadata` (PEP 658) |
| npm | `npm-registry` | packument, dist-tags | — |
| Maven | `maven2` | `maven-metadata.xml`, POM, `.module` | — |
| NuGet | `nuget-v3` | service index, registration | — |
| Go | `goproxy` | `@v/list`, `.info`, `.mod` | — |
| crates | `cargo-sparse` | sparse-индекс и API `/api/v1/crates/<имя>` (адрес — в `config.api_url`) | нет описаний, ссылок и лицензий |
| RPM | `rpm-repodata` | `repomd.xml` и файлы repodata | — |

- **Ленты изменений** (`_changes` npm, catalog NuGet, индекс Go) есть только у публичных реестров. Для источника без ленты детектор опрашивает каждый пакет условным запросом; это уже реализовано (SPEC-DAILY-UPDATE §3).
- **PyPI: корневой индекс.** Детектор `pypi-warehouse` читает корневой Simple-индекс с `_last-serial` каждого проекта, а проект, которого в индексе нет, считает пропавшим. Реактивный прокси может не отдавать корневой индекс или отдавать в нём только то, что уже в кэше; тогда пакеты каталога будут ошибочно помечены недоступными. Варианты: прокси пропускает корневой индекс PyPI как есть, либо источник прокси опрашивается по проектам. Выбор делается по итогам пакета Х2.
- **Свежесть.** Реактивный прокси обновляет метаданные по своим правилам кэша. Задержка каталога = срок кэша прокси + суточный цикл. Срок кэша фиксируется в документе, когда станет известен.
- **Нагрузка.** Суточный обход — это запросы прокси в интернет за метаданными всех пакетов каталога (на стенде их около трёх тысяч). Артефакты сервис не скачивает (SPEC-MULTI-ECOSYSTEM §0.3).

### 4.3 Учётная запись сервиса

- PackageHub ходит в прокси под отдельной учётной записью вида `service`.
- Прокси **не включает её запросы в выгрузку скачиваний** и не передаёт их в учёт, по которому оповещает корпоративная система. Иначе журнал перестанет отражать работу людей, а сервис начнёт получать уведомления об уязвимостях всего каталога.
- Запросы помечены `User-Agent: PackageHub/<версия>`.

### 4.4 Авторизация к источникам

Сейчас `auth_type` применяется только в RPM-воркере; адаптеры остальных шести экосистем шлют запросы без учётных данных ([обзор](./REVIEW-2026-11.md), F12). На Э0 `basic` и `bearer` реализуются в общем HTTP-клиенте для всех протоколов; секрет читается так же, как в RPM-воркере (файл с именем `credentials_ref` в каталоге секретов). Сочетание, которое не поддержано, отклоняется при сохранении источника.

## 5. Статус версии в контуре

### 5.1 Два факта, а не одна оценка

На Э0 у версии два независимых факта от прокси:

| Факт | Значения | Откуда |
|---|---|---|
| Блокировка | заблокирована (с причиной) / не заблокирована | снимок блокировок |
| Присутствие | отдавалась прокси (первое и последнее обращение) / не запрашивалась | журнал скачиваний |

Как это показывается:

| Блокировка | Присутствие | Подпись |
|---|---|---|
| есть | было | «Заблокирована. Раньше скачивалась» |
| есть | не было | «Заблокирована» |
| нет | было | «Не заблокирована, есть в контуре» |
| нет | не было | «Не заблокирована, в контур не попадала» |

- **«Не заблокирована» — не «разрешена».** Прокси реактивный: незаблокированную версию он скачает по запросу, а проверка корпоративной системой идёт после. Слова «разрешена» и «проверена» на Э0 в интерфейсе не используются. Оценка появится на Э1 отдельным полем, не меняя этих двух.
- **Статус версии у источника** (`active`, `yanked`, `deprecated` и другие, SPEC-DAILY-UPDATE §4.2) остаётся как есть. Блокировка прокси — отдельное измерение, в `package_versions.status` она не записывается.
- **Версии вне каталога** имеют те же два факта: блокировки и агрегаты скачиваний хранятся по экосистеме, нормализованному имени и версии, без ссылки на строку пакета.

### 5.2 Данные

Набросок; точная схема и миграция пишутся при принятии этапа.

| Таблица | Что хранит |
|---|---|
| `proxy_blocks` | блокировки с историей: идентификатор прокси, экосистема, имя, цель, причина, вид причины, ссылка, `blocked_at`, `first_seen_at`, `lifted_at` |
| `proxy_version_usage` | агрегаты по версии: первое и последнее обращение, число выдач, число отказов |
| `proxy_link_state` | позиция чтения журнала, ревизия снимка блокировок, время последнего успеха, предупреждения |

### 5.3 События

Появление и снятие блокировки для пакета каталога записывается в журнал событий двумя новыми видами: `proxy_blocked` и `proxy_unblocked` (версия пустая, если заблокирован пакет целиком). События видны на странице обновлений вместе с остальными. Эту часть можно отложить, не задерживая остальной этап.

## 6. API и интерфейс

Поля и коды ответов окончательно описываются в `SPEC-MVP-API.md` при принятии этапа.

### 6.1 Статус по purl

Сначала ответ для машин: его читают сборки, скрипты и агенты; карточка показывает то же самое человеку.

- `GET /api/v1/proxy/status?purl=<purl>` — одна версия или пакет.
- `POST /api/v1/proxy/status` с телом `{"purls": [...]}` — до 500 purl за запрос.

```json
{
  "purl": "pkg:npm/%40scope/pkg@4.17.21",
  "in_catalog": true,
  "blocked": true,
  "block": {
    "scope": "versions",
    "reason_kind": "vulnerability",
    "reason": "Удалённое выполнение кода, исправлено в 4.17.22",
    "reference": "GHSA-xxxx-xxxx-xxxx",
    "since": "2026-11-14T08:00:00Z"
  },
  "downloaded": {"first_at": "2026-03-02T09:10:00Z", "last_at": "2026-11-13T17:25:00Z"},
  "latest_unblocked": "4.17.22",
  "url": "https://packagehub.example/b/npm/@scope/pkg@4.17.21"
}
```

- Ответ есть **для любого** корректного purl, в том числе для пакета вне каталога: тогда `in_catalog: false`, а `latest_unblocked` пуст.
- `latest_unblocked` — старшая стабильная незаблокированная версия пакета каталога. Это подсказка, а не замена: совместимость с остальным графом она не проверяет (это Э1 и Э4).
- Для purl без версии `blocked` истинно, только если заблокирован пакет целиком; дополнительно отдаётся число заблокированных версий.
- Чтение открыто, как у остального API. В ответе нет учётных записей.

### 6.2 Существующие ответы

- Карточка пакета и список версий получают признак блокировки версии; сведения о версии — тот же объект, что в разделе 6.1.
- `GET /api/v1/admin/sync/status` получает блок состояния связки: позиции, отставание, предупреждения.

### 6.3 Охват

`GET /api/v1/proxy/coverage?days=30` — отчёт: сколько скачанных пакетов и версий есть в каталоге (по числу пакетов и с весом по числу обращений), список самых запрашиваемых пакетов вне каталога. Список можно передать в существующий `POST /admin/packages`.

### 6.4 Интерфейс

- **Карточка.** Метка блокировки у версии в шапке и в списке версий, причина и ссылка на бюллетень, `latest_unblocked` как подсказка.
- **Страница статуса** `/b/{экосистема}/{имя}[@{версия}]`. На неё ведёт ссылка из отказа прокси. Открывается для любого пакета: для пакета каталога показывает причину и ведёт на карточку, для пакета вне каталога показывает причину и то, что известно от прокси. Не отвечает «не найдено» на корректный адрес.
- **Страница обновлений.** События блокировки и разблокировки (раздел 5.3).

## 7. Отказ прокси

### 7.1 Что меняется

Только текст. Код ответа и условия отказа остаются такими, какие у прокси сейчас.

```
Blocked by security policy (vulnerability, GHSA-xxxx-xxxx-xxxx).
Details: https://packagehub.example/b/npm/@scope/pkg@4.17.21
```

- **Ссылка строится на прокси по шаблону** из адреса PackageHub, экосистемы, имени и версии. Прокси при отказе к PackageHub не обращается.
- **Формат ссылки** повторяет purl без квалификаторов: `/b/{экосистема}/{имя}[@{версия}]`. Версия отделяется последним знаком `@`, не стоящим в начале имени (у npm с `@` начинается область имён). Адрес короткий, чтобы его можно было перенести из терминала вручную.
- **Текст на латинице.** Часть клиентов показывает только строку статуса HTTP, а она не допускает кириллицу. Русское объяснение — на странице по ссылке.

### 7.2 Где клиент покажет текст

Менеджеры пакетов по-разному показывают отказ сервера. Таблица — `гипотеза` по общим сведениям о клиентах; проверка на настоящих клиентах входит в этап (пакет П3), и по её итогам таблица заменяется фактами.

| Клиент | Что, предположительно, видит пользователь | Куда класть текст |
|---|---|---|
| pip, uv | код и строку статуса | строка статуса и тело |
| npm, pnpm, yarn | сообщение из JSON-тела ошибки | тело в формате ошибки реестра |
| Maven, Gradle | код и строку статуса | строка статуса |
| Go | текст тела ответа | тело `text/plain` |
| NuGet | код и строку статуса | строка статуса |
| Cargo | код, иногда тело | тело и строка статуса |
| dnf, yum | код | строка статуса; ссылку, возможно, не покажет |

Если клиент не показывает ни тело, ни строку статуса, ссылка до пользователя не дойдёт. Для таких экосистем остаётся поиск по имени пакета в PackageHub; это фиксируется как ограничение.

## 8. Проверка и стенд

- **Эмулятор выгрузки.** Тесты по умолчанию идут без сети, поэтому ответы `/export/v1/…` записываются как фикстуры (`backend/tests/fixtures/http/`). Те же примеры — контрактные для прокси: его выгрузка проверяется на соответствие им.
- **Случаи для тестов:** пустой и резко уменьшившийся снимок; диапазон, который не разбирается; повтор записей журнала; запись с неизвестной экосистемой; блокировка пакета вне каталога; смена цели блокировки; простой PackageHub дольше срока хранения журнала.
- **Источники через прокси.** Прогон семи экосистем через прокси (или его тестовый экземпляр) с записью расхождений с публичными источниками — отдельный пакет работ и первый по порядку.
- **Стенд.** На стенде прокси нет. Вариант по умолчанию — эмулятор рядом со стендом; связка с настоящим прокси проверяется в контуре (допущение А9).

## 9. Что измеряем

Э0 даёт исходные значения, от которых потом считается эффект этапов Э2–Э4.

| Мера | Как считается |
|---|---|
| Охват каталога | доля скачанных за 30 дней пакетов и версий, которые есть в каталоге; отдельно с весом по обращениям |
| Отказы сегодня | число запросов с исходом `blocked` в сутки и число затронутых версий; это исходное значение меры «узнал до, а не после» |
| Запросы после блокировки | сколько дней после блокировки версию продолжают запрашивать; исходное значение меры «время отреагировать» |
| Работа связки | отставание чтения блокировок и журнала; доля неразобранных записей |
| Переходы по ссылке | число открытий страницы статуса: доходит ли ссылка из отказа до людей |

Метрики связки добавляются к существующим (`/metrics`): отставание, число действующих блокировок, число записей по исходам, число отклонённых записей.

## 12. Открытые решения и недостающие факты

### 12.1 Решения владельца

К каждому — вариант по умолчанию, на котором построен черновик.

1. **Хранить ли в PackageHub учётные записи скачавших.** По умолчанию: на Э0 нет. Журнал «кто скачал» остаётся на прокси, PackageHub хранит агрегаты. Причина: чтение API открыто и ролей нет до этапа Э2. Следствие: к этапу Э4 прокси должен хранить журнал достаточно долго, чтобы найти скачавших затронутую версию; срок нужно назначить сейчас.
2. **Кому видна причина блокировки.** По умолчанию: всем; в выгрузку попадает только текст для пользователей, внутренние заметки остаются на прокси.
3. **Пополнять ли каталог скачанными пакетами.** По умолчанию: на Э0 нет, только отчёт об охвате и ручное добавление существующей командой. Автоматическая оценка любого пакета — предмет Э1 и пересмотра D1.
4. **События блокировки на странице обновлений** (пакет Х7). По умолчанию: да, но после остального.

### 12.2 Факты о прокси

Уточняют допущения раздела 2; первые три нужны до начала работ.

1. Репозиторный это прокси или HTTP-прокси общего назначения (А1)? Какие экосистемы он обслуживает?
2. Как он определяет пакет и версию запрошенного файла (А2)?
3. Где и в каком виде хранятся блокировки; попадают ли в них причина и дата; как туда приходит решение корпоративной системы (А3, А4)?
4. Что пишется в журнал и сколько он хранится (А5, А6)?
5. Как опознаётся пользователь и как данные о скачивании попадают в корпоративную систему (А7, раздел 4.3)?
6. Что прокси отвечает при отказе сейчас: код, тело?
7. Срок кэша метаданных; пропускает ли он JSON API PyPI и API crates.io (А8)?
8. Есть ли тестовый экземпляр (А9)?
