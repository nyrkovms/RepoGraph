**База:** `main` @ `41bf257` (после PR #80)

## Как читать

**Метод.** Код прочитан по пяти областям (API, запись и фоновые задачи, экосистемы и resolve, frontend, тесты и эксплуатация), страницы и API проверены на живом стенде. Нагрузочных прогонов, `EXPLAIN` и запуска тестов не было.

**Чем подтверждено.** У каждого пункта стоит одна из трёх отметок:

- `стенд` — воспроизведено или измерено на стенде;
- `код` — видно при чтении кода, без запуска;
- `гипотеза` — следует из кода, но зависит от объёма данных или нагрузки и требует прогона.

**Приоритет.**

- **P1** — теряются данные или мониторинг, сервис можно положить одним запросом, либо пункт блокирует выкат.
- **P2** — заметно пользователю или дежурному, есть обходной путь.
- **P3** — качество, сопровождение, мелкие неточности.

**Что уже известно и здесь не повторяется:** этап E7 (страница Resolve на старом формате, алиасы `/packages/pypi/{name}`, типы в `connectors/base.py`), этапы U3–U5 дайджеста, сбор уязвимостей только для PyPI (D6), Gradle Module Metadata (Q15), issue #33, невыполненные пункты [PRODUCTION-CHECKLIST](../PRODUCTION-CHECKLIST.md). Они упоминаются только там, где обзор добавляет к ним новое.

**Баги.** На десять подтверждённых багов заведены issues #81–#90 (раздел 10). Остальные пункты — улучшения и риски: issue заводится, когда пункт берётся в работу.

## 1. Итог

Проект делает то, что обещают спецификации: каталог из семи экосистем наполняется, обновляется раз в сутки без сбоев (125 успешных прогонов из 126, один `partial`), карточка пакета и дайджест отвечают на вопросы аналитика, resolve сверен с нативными инструментами на 38 эталонных проектах. Инженерная дисциплина высокая: единый путь записи, офлайн-CI на записанных ответах источников, снимок OpenAPI, проверка миграций туда и обратно, `mypy --strict` для плагинов.

Слабые места сосредоточены в четырёх зонах:

1. **Мониторинг слепнет там, где он нужен.** Метрики ежедневного прогона не доходят до `/metrics` (#83), ошибки 500 не считаются, а число рядов растёт от обычной работы в браузере (#81). Алерты из чек-листа выката на таких данных построить нельзя.
2. **Открытые эндпоинты не ограничены по стоимости.** Дерево зависимостей раскрывает общие поддеревья многократно (775 узлов при 38 уникальных пакетах), ленивая загрузка из GET-запросов и `POST /resolve` не имеют ни лимита частоты, ни общего ограничения параллелизма. Несколько одновременных запросов исчерпывают пул из 15 соединений с БД.
3. **Отказы в середине работы обрабатываются неполно.** Пакеты упавшего источника помечаются как неповторяемые (#84), убитый воркер теряет ежедневный прогон и на 6 часов блокирует ручной запуск, ленивая загрузка зависимостей не защищена от гонки (#87).
4. **Пути в прод нет.** В репозитории только dev-окружение: frontend на Vite dev server с адресом API `localhost`, контейнеры под root, дефолтные пароли, бэкапы без ротации и проверки.

Из функциональных пробелов главный — **страница Resolve работает только для PyPI**, хотя API умеет все семь экосистем. Это часть E7, но для пользователя это самая заметная разница между возможностями сервера и интерфейса.

### Что получилось особенно хорошо

- **Единый путь записи.** `sync_package` — единственный писатель, события считаются из снимков «до» и «после» в той же транзакции (`backend/app/fetcher/pipeline.py`, `fetcher/events.py`).
- **Дисциплина ошибок источника.** Отсутствием считается только 404; 403, 5xx и таймауты не кэшируются как «пакета нет»; деградировавший приоритетный источник останавливает обнаружение и не даёт подменить пакет из источника ниже (`fetcher/discovery.py`).
- **Resolve, сверенный с нативными инструментами.** Каждый резолвер называет, какой инструмент эмулирует, и проверен на эталонах: pypi 2, npm 3, crates 4, go 5, nuget 8, maven 8, rpm 8 (`backend/tests/reference/`). Схемы версий сверены с векторами, сгенерированными самими инструментами.
- **Частичный граф вместо отказа.** Проблема одного узла попадает в `errors` узла и `warnings` ответа, остальной граф отдаётся.
- **Правила честности данных** из SPEC-CATALOG-PAGES §3 соблюдены в интерфейсе: «in this catalog», «a lower bound», три состояния блока Security, «Not published by the source».
- **Состояние в URL и защита от гонок во frontend.** Фильтры поиска и Updates, вкладка и версия карточки живут в адресе; запоздавшие ответы отбрасываются, на это есть отдельный тест (`PackageRaces.test.jsx`).
- **Офлайн-CI.** Интеграционные тесты и smoke идут по записанным ответам, непокрытый запрос валит сборку; ночной прогон ходит в живые источники.
- **Защита контрактов.** Снимок OpenAPI, тест соответствия lock-файлу, `check_migrations.sh` (base → head → downgrade → head), проверка ссылок в документах.

## 4. Функциональные пробелы

**F1 (P1, стенд). Resolve в интерфейсе — только PyPI.** Страница отправляет `ecosystem: "pypi"` и старый формат (`frontend/src/pages/ResolvePage.jsx:233`). Шесть экосистем, режим `lock`, профили источников, предупреждения и ошибки узлов из интерфейса недоступны, хотя формы окружения для всех экосистем уже есть на вкладке Dependencies. Кроме того, у результата нет ссылок на карточки пакетов, нет плоского списка и копирования, состояние не хранится в URL, разбор ввода не показывает ошибок: строка с маркером окружения, комментарием или `-r file` уходит на сервер как есть (`:167-192`). *Что сделать:* поднять приоритет E7(а); переиспользовать `packageEnv.js` и компоненты окружения карточки; показать разобранный список перед запросом.

**F2 (P2, стенд). Источники и профили не видны в интерфейсе.** `GET /registries` и `/profiles` есть, страницы нет. Аналитик не может узнать, какие источники включены, какие деградировали и почему, не обращаясь к admin API. *Что сделать:* страница «Sources» только для чтения: источник, протокол, приоритет, число пакетов, время последнего ответа, состояние предохранителя.

**F3 (P2, код, #85). Presence probe по расписанию идёт только для PyPI.** Пакеты остальных экосистем не проверяются на появление в других источниках профиля.

**F4 (P2, код). На вкладке Sources нет артефактов.** SPEC-CATALOG-PAGES §5 обещает «реестры и артефакты текущей версии»; `SourcesTab.jsx` показывает только реестры. Файлы, размеры и контрольные суммы лежат в БД (468 тыс. строк `artifacts`) и отдаются API, но в интерфейс не выведены. *Что сделать:* таблица файлов с размером и sha256 либо правка спеки.

**F5 (P2, стенд). Строка обновления показывает пару версий, к которой не относится метка.** Пример со стенда: `microsoft.bcl.asyncinterfaces 11.0.0-rc.3 → 11.0.0 major`. Слева стоит `previous_version` (ближайшая меньшая, в том числе пререлиз), а `major` посчитан от ближайшей стабильной (10.0.x), как и задано в SPEC-DAILY-UPDATE §4.3. Читатель видит «rc → релиз» с подписью «New major version: expect breaking changes», а ссылка Compare сравнивает rc с релизом, где различий почти нет. *Что сделать:* хранить в `details` стабильную опору (`previous_stable_version`), показывать её в строке и вести на неё Compare; пререлиз оставить в раскрытой истории.

**F6 (P2, стенд). «checked» на вкладке Sources означает «последний раз перечитан».** У Django стоит `checked 04.11.2026`, хотя источник опрашивается каждую ночь: `package_registries.checked_at` обновляется только при перезаписи пакета (`pipeline.py:432-451`). Это тот же случай, что правило 5 из SPEC-CATALOG-PAGES §3 про `last_sync_at`. *Что сделать:* подписать поле как «last changed» и показывать рядом время последнего успешного прогона экосистемы, либо обновлять `checked_at` всем пакетам, которые детектор признал неизменными.

**F7 (P3, стенд). Нет страницы «не найдено» и понятного текста для отсутствующего пакета.** Неизвестный адрес показывает пустую страницу (`App.jsx:27-36`, маршрута `*` нет). Карточка отсутствующего пакета показывает `HTTP 404` без объяснения, что каталог курируемый и пакет в него не добавлен. Заголовок вкладки браузера всегда `PackageHub`.

**F8 (P3, стенд). Порядок версий в выпадающем списке — по дате выпуска.** `/versions` сортирует по `release_date` (`package_detail.py:244`), поэтому у Django список начинается с `5.2.19, 6.0.10, 6.1.3, 5.2.18…`; выбранная последняя версия стоит третьей. То же в селекторе «From» на вкладке Compare. *Что сделать:* сортировать по `sort_key` или группировать по линейкам, как на вкладке Versions.

**F9 (P3, код). Нет выгрузки.** Таблицы зависимостей, зависимых пакетов и результат resolve нельзя ни скопировать, ни выгрузить в CSV или JSON; столбцы не сортируются.

**F10 (P3, код). Подпись про уязвимости на главной зашита в код.** `Security advisories: PyPI only` (`HomePage.jsx:324`) перестанет быть правдой при подключении второго источника; карточка берёт охват из поля `coverage`. В списках `has_vulnerabilities: false` для шести экосистем читается как «проверено, чисто», а фильтр `has_vulnerabilities=false` возвращает их все (`packages.py:183-188, 297-300`). *Что сделать:* в списке `bool | null`, на главной строить подпись из сводки.

**F11 (P3, стенд). Наследие PyPI в верхнем уровне ответов.** `/stats` на верхнем уровне отдаёт счётчики одного PyPI, `/admin/sync/status` смешивает последний прогон любой операции (`packages_total: 965` — это RPM) с курсором и `last_success_at` источника `pypi`. Поведение задокументировано, но вводит в заблуждение. *Что сделать:* удалить вместе с алиасами в E7(б).

**F12 (P3, код). Авторизация закрытых источников принимается, но не применяется.** `auth_type=basic|bearer` можно задать источнику любой экосистемы, а используют его только RPM-воркер (`basic`, `tls_client_cert`). Адаптеры остальных шести экосистем шлют запросы без учётных данных, `bearer` не работает нигде. Корпоративные репозитории отложены решением D4, но API об этом не говорит. *Что сделать:* отвечать 422 на неподдерживаемое сочетание протокола и `auth_type`.

## 5. Запись, фоновые задачи, модель данных

**W1 (P1, код, #84). Пакеты деградировавшего источника помечаются неповторяемыми.** `SourceDegraded` не входит в список повторяемых ошибок; строка `sync_failures` получает `retryable = false`, а ранее повторяемая строка теряет этот признак при следующей встрече с открытым предохранителем. Для экосистем с лентой изменений (npm, NuGet, Go) пакет ждёт недельной сверки. Противоречит SPEC-DAILY-UPDATE §2.2, шаг 3. Туда же попадают обрыв соединения с БД и нарушение уникальности из пунктов W5 и W6.

**W2 (P1, стенд, #83). Метрики, записанные в воркере, не видны.** `packagehub_daily_update_*`, `packagehub_package_events_total` и `packagehub_sync_duration_seconds` на стенде пусты после семи успешных прогонов: значения остаются в процессе Celery.

**W3 (P1, код, #87). Гонка в ленивой загрузке зависимостей версии.** `ensure_version_dependencies` не берёт блокировку пакета, у таблицы `dependencies` нет уникального ограничения. На стенде таких дублей нет: 33 полностью совпадающие строки повторяют то, что источник сам перечислил дважды.

**W4 (P1, код). Убитый воркер теряет прогон.** `finish_run` вызывается только на штатном пути. После SIGKILL, OOM или остановки воркера строка `runs` остаётся в `running`, и шесть часов любой запуск ежедневного обновления, включая ручной, возвращает `skipped` (`services/runs.py:14-33`). В Celery не заданы `acks_late`, `reject_on_worker_lost` и лимиты времени (`celery_app.py:54-60`): задача потеряна, beat запустит её только завтра. *Что сделать:* отметка активности в `runs` и сторож, закрывающий прогоны без отметки дольше N минут; `task_acks_late` для идемпотентных задач; `soft_time_limit` и `time_limit` на задачу.

**W5 (P2, код). `sync_states` пишется через «прочитать, затем вставить».** Первая запись по новому источнику из нескольких задач одновременно даёт нарушение уникальности (`pipeline.py:1191-1210`); строка состояния не создаётся при создании источника. Каждая успешная запись пакета сбрасывает счётчик предохранителя, поэтому задача, начатая до отказа, закрывает его раньше времени. *Что сделать:* `INSERT … ON CONFLICT DO UPDATE`, создавать строку вместе с источником, сбрасывать счётчик только ответом источника.

**W6 (P2, код). Уязвимости и авторы пишутся без защиты от гонки.** `vulnerabilities.source_id` уникален, а один бюллетень часто относится к нескольким пакетам: два параллельных синка получают нарушение уникальности, порядок вставки не задан, возможен deadlock (`pipeline.py:760-809`). У `authors` уникального ограничения нет, гонка молча создаёт дубли. *Что сделать:* `ON CONFLICT (source_id)`, сортировка по ключу, уникальный индекс авторов.

**W7 (P2, код). `retry-failed-sync` не защищён от наложения.** Задача запускается каждые 15 минут, берёт 100 строк и обрабатывает их последовательно; если пачка идёт дольше, следующий запуск берёт те же строки, и восемь попыток расходуются вдвое быстрее (`tasks/retry_failed.py:41-66`). Пропускная способность около 9,6 тыс. пакетов в сутки. *Что сделать:* `FOR UPDATE SKIP LOCKED` либо сдвиг `next_retry_at` при выборке, ограниченная параллельность, как у ежедневного обновления.

**W8 (P2, код). Фоновые дозаполнения перезаписывают `raw_metadata` устаревшей копией.** `release_dates` и `crates_api` читают строки, ждут сеть и пишут весь jsonb целиком без блокировки пакета (`tasks/release_dates.py:44-83`, `tasks/crates_api.py:38-67`); параллельная запись пакета теряется. Обе задачи идут раз в минуту без защиты от наложения. *Что сделать:* обновлять поле в SQL (`||`, `jsonb_set`) с условием и брать блокировку пакета.

**W9 (P2, код). Одна очередь на всё.** Ежедневное обновление, повторы, минутные дозаполнения и задачи, запущенные из API, делят один пул воркеров; у минутных задач нет `expires`, после простоя воркера они выполняются пачкой. Ежедневный прогон — одна задача на все экосистемы подряд: ошибка до начала обработки экосистемы пропускает остальные (`daily_update.py:298`). *Что сделать:* очереди `updates`, `interactive`, `background`; `expires` у периодических задач; задача на экосистему.

**W10 (P2, код). Нет таймаутов на уровне БД.** Ожидание блокировки пакета (`pg_advisory_xact_lock`) не ограничено, `statement_timeout` и `idle_in_transaction_session_timeout` не заданы. Зависший держатель блокировки останавливает всех писателей пакета и прогон без лимита времени. *Что сделать:* `SET LOCAL lock_timeout` перед блокировкой с повтором, таймауты на движке.

**W11 (P2, код). Каждый синк пересоздаёт зависимости и артефакты всех версий.** `_replace_dependency_rows` и `_replace_artifacts` удаляют и вставляют строки, даже если ничего не изменилось (`pipeline.py:679-738`); у npm-пакета с тысячами версий это тысячи строк на каждое обновление. `artifacts` уже самая большая таблица стенда (319 МБ). *Что сделать:* пропускать версии с неизменным `metadata_digest`, артефакты сравнивать по ключу.

**W12 (P2, код). Состояние «зависимости недоступны» не пересматривается.** Для Maven, Go и npm разовый 404 на документ версии (задержка CDN, сбой зеркала) навсегда ставит `dependencies_state = unavailable`; повторная проверка есть только для PyPI-артефактов с файлом метаданных (`pipeline.py:835-838, 984-1005`). *Что сделать:* запоминать время и повторять после TTL или при следующем синке пакета.

**W13 (P2, код). Детекторы изменений глотают ошибки по пакету.** При сбое запроса детектор отвечает «не изменился» и пишет предупреждение в лог (`maven2.py:579-582`, аналогично npm, crates, pypi-simple, go, nuget). Полный отказ источника на этапе обнаружения может дать зелёный прогон без изменений; предохранитель эти ошибки не считает. Влияние на итоговый статус прогона не проверялось. *Что сделать:* считать долю ошибок за прогон и выше порога записывать отказ источника.

**W14 (P2, код, #88). Go: сбой чтения `go.mod` при синке стирает отзыв версий.** Ошибка сети превращается в «у модуля нет go.mod».

**W15 (P2, код). Индексы под запросы, которые уже выполняются.** Нет индекса на `package_events.run_id`, по которому `finish_run` считает события каждого прогона (`services/runs.py:52`); нет частичных индексов для минутных выборок версий без даты и крейтов без отметки API. `find_package` оборачивает `NOT NULL`-колонку в `coalesce`, что может мешать уникальному индексу (`pipeline.py:272-279`, гипотеза). Миграция — защищённый путь, нужна задача с её указанием.

**W16 (P3, код). Один 404 помечает пакет недоступным.** Разовый ложный ответ источника даёт событие `project_unavailable`, следующий прогон — `project_restored`: шум в дайджесте. `mark_unavailable` не берёт блокировку пакета. *Что сделать:* требовать второго промаха подряд.

**W17 (P3, код). Длина колонок.** Значение источника длиннее колонки (`String(2048)` для ссылок, `String(128)` для версии, `String(64)` для dist-tag и др.) валит запись всего пакета, как в #77, и ошибка неповторяема. *Что сделать:* обрезка в одном месте на границе записи или `Text`.

**W18 (P3, код). Нет очистки служебных таблиц.** `runs`, отработанные `sync_failures` (traceback до 16 КБ), `source_documents` растут без ограничений; индекс `idx_sync_failures_last_seen` под очистку есть, задачи нет. `packages` занимает 72 МБ на 3 022 строки из-за `raw_metadata`: стоит проверить, что запросы списков не читают эту колонку.

**W19 (P3, код). Мелочи прогона.** Ежедневное обновление не вызывает `progress_run`, и `/admin/sync/status` показывает нули до конца прогона; `_update_many` создаёт корутину на каждый пакет сразу; `asyncio.gather` без `return_exceptions`. Бюллетени уязвимостей обновляются частично (`summary`, `severity`, `link` не освежаются), `affected_versions` всегда пуст (`pipeline.py:804-809`). Предохранитель после паузы пускает все запросы сразу, `Retry-After` не учитывается.

## 6. API: производительность и защита

**A1 (P1, стенд). Дерево зависимостей не ограничено и раскрывает общие поддеревья повторно.** `visited` ведётся по пути, поэтому пакет, достижимый N путями, раскрывается N раз; глубина по умолчанию 200, счётчика узлов нет (`package_detail.py:1056-1073`). На стенде: 860 узлов при 56 уникальных пакетах (Maven), 775 при 38 (NuGet). Каждый узел стоит нескольких последовательных запросов к БД. Цель 500 мс для NuGet не выполняется уже при `depth=5`. *Что сделать:* мемоизация поддерева по версии и окружению в пределах запроса с пометкой повтора, жёсткий лимит узлов с `truncated: true`, выборка уровня одним запросом.

**A2 (P1, код). Ленивая загрузка из GET-запросов не ограничена и держит соединение с БД.** Чтение карточки или дерева неизвестного пакета идёт в источник (таймаут 10 с, три повтора), сессия занята всё это время; пул — 5 соединений плюс 10 сверх (`db.py:11`). Лимит 500 из SPEC-MVP-API §2.5 действует только в resolve. Несколько одновременных запросов к несуществующим именам или глубоким деревьям исчерпывают пул, после чего не отвечают поиск и остальное. *Что сделать:* бюджет ленивых загрузок на запрос, общий семафор и лимит частоты (помощник `wait_turn` в Redis уже есть), настраиваемый пул, отпускать соединение перед походом в источник.

**A3 (P1, стенд). `used_by` агрегируется в пути запроса без индекса.** На `dependencies.resolved_package_id` индекса нет (проверено на стенде), а `used_by_counts` вызывается на каждой странице списка и поиска, в сводке Updates, в overview и четыре раза в `/catalog/summary` (`services/usage.py:39-57`). *Что сделать:* частичный индекс новой миграцией; затем хранимый счётчик, который обновляет pipeline.

**A4 (P2, гипотеза). Транзитивное замыкание графа строится на каждый запрос.** Overview делает три рекурсивных CTE, `/dependents` — ещё по одному на страницу плюс полное множество зависимых (`services/usage.py`, `package_detail.py:543-554`). У популярного пакета список идентификаторов в `IN (…)` может превысить предел 32 767 параметров asyncpg и дать 500. На стенде `/dependents` для `typing-extensions` — 670 мс. *Что сделать:* `EXPLAIN` на стенде; постраничный вывод соединением с CTE; кэш замыкания по ревизии каталога.

**A5 (P2, код). Поиск не использует триграммный индекс.** Условие — `lower(…) LIKE '%q%'` по имени и описанию через `OR`, а индекс построен на голой `normalized_name` (`packages.py:166-178`). Сейчас это полный просмотр 3 тыс. строк и 40–100 мс; с ростом каталога цель 200 мс окажется под угрозой. У `q` нет ограничения длины. *Что сделать:* индексы по тем выражениям, которые стоят в запросе, либо полнотекстовый поиск для описаний.

**A6 (P2, стенд). `/updates/summary` принимает любое окно.** Запрос с `since=2000-01-01` читает весь журнал событий в память и отдаёт одним списком: 234 КБ и 0,5 с на 4 тыс. событий. Хранение журнала не ограничено (SPEC-DAILY-UPDATE §4). *Что сделать:* предел окна (например, 31 день) с 422 либо пагинация.

**A7 (P2, код). Тяжёлые открытые агрегаты без кэша.** `/stats`, `/catalog/summary` (около восьми запросов) и `/metrics` (обращения к БД на каждый сбор) считаются заново на каждый вызов. *Что сделать:* кэш в Redis на 30–60 секунд.

**A8 (P1, стенд, #81). Число рядов метрик растёт от обычной работы.** Каждый CORS-preflight и каждый адрес без маршрута создают новый ряд; ответы 500 от необработанных исключений не считаются.

**A9 (P2, стенд, #82). Admin API отвечает 500 на токен с не-ASCII символом.**

**A10 (P2, код, #90). `POST /resolve` отдаёт клиенту текст внутренних исключений.** Поле `trace_id` при этом всегда `null`.

**A11 (P2, код). Проверка подключения источника не ограничивает адрес.** `base_url` и адреса из `config` принимают любой `http(s)`-хост, включая внутренние и служебные адреса; адаптеры следуют перенаправлениям; ответ `POST /admin/registries/{slug}/test` содержит текст ошибки и время. Эндпоинт закрыт admin-токеном, но dev-значение токена опубликовано в README, а проверка дефолтов при старте срабатывает только при `APP_ENV=production`. *Что сделать:* по умолчанию запрещать loopback, link-local и частные сети с явным списком исключений; грубая ошибка в ответе; отказ стартовать с dev-токеном вне локальной разработки.

**A12 (P2, код). Нет ограничения частоты ни на одном эндпоинте.** `services/rate_limit.py` используют только адаптеры источников. Для внутреннего контура это допустимо, пока запросы дёшевы; пункты A1, A2 и R1 показывают, что это не так.

**A13 (P3, гипотеза). Числа вне диапазона в курсоре дают 500.** Проверка типа есть, проверки диапазона нет: значение больше int64 дойдёт до asyncpg (`packages.py:216-220, 279`, `updates.py:384-386`). На стенде не воспроизводилось.

**A14 (P3, код). Модели запросов не ограничивают размер и молча игнорируют лишние поля.** `managed`, `extras`, `environment`, `dependencies` в resolve без `max_length`; ни одна модель не задаёт `extra="forbid"`, поэтому опечатка в имени поля (`option` вместо `options`) приводит к значениям по умолчанию без ошибки.

**A15 (P3, код). Ошибки валидации `/resolve` приходят не в конверте.** SPEC-MVP-API §2.4 требует конверт для `POST /resolve`, но отказ FastAPI при разборе тела возвращается как `{"detail": […]}`.

**A16 (P3, код). Окружение дерева PyPI не проверяется.** Неверный `python_version` молча расширяет дерево (исключение маркера трактуется как «подходит»), `python_full_version` для `3.12.1` получается `3.12.1.0`, неизвестная `os` даёт пустые значения. Остальные экосистемы отвечают 422 (`package_detail.py:806-865`).

**A17 (P3, код). Несогласованности контракта.** Даты местами строкой, местами `datetime`; `profile` принимают только два маршрута из семи; `sort=downloads_total` есть, а поля в элементах нет; курсор не привязан к фильтрам и принимается с другими; неразборчивые координаты дают 404 там, где `/purl` даёт 422. Открытый `GET /registries` отдаёт `credentials_ref`, `config` и `last_error` с текстом ошибок источника.

**A18 (P3, код). `package_detail.py` — 1 196 строк.** В одном файле маршруты, вычисление маркеров PyPI, построение окружения пятью ветками по экосистемам, строитель дерева и логика поставщиков RPM. Ветки `if ecosystem == …` вне плагинов есть ещё в десятке мест (`resolver/service.py`, `services/release_lines.py`, `tasks/seed.py`, `api/v1/updates.py` и др.). *Что сделать:* вынести дерево и маркеры в отдельные модули (перенос отдельным коммитом), окружение из параметров запроса строить методом плагина.

## 7. Resolve и экосистемы

**R1 (P1, код). `POST /resolve` открыт, дорог и не ограничен по параллельности.** Запрос может держать соединение с БД до 130 секунд и добавить в каталог до 500 пакетов с `origin=discovered`; пул потоков резолвера PyPI — 8, отсчёт таймаута начинается до постановки в очередь (`pypi/resolver.py:282`). Пятнадцать одновременных запросов исчерпывают пул БД. *Что сделать:* семафор на экосистему, меньший таймаут по умолчанию для анонимных запросов, лимит частоты; отдельно решить, должны ли анонимные запросы пополнять каталог (уже отмечено в чек-листе выката как риск).

**R2 (P1, код). Недоступный rpm-worker: запрос ждёт весь таймаут, задачи копятся.** Клиент отправляет задачу без `expires` и не отзывает её по таймауту (`ecosystems/rpm/client.py:32-42`): при остановленном воркере пользователь ждёт 30–120 секунд, а после возврата воркер выполняет resolve, которых никто не ждёт. `fetch_package` ждёт до 600 секунд в потоке общего пула. *Что сделать:* `expires`, отзыв по таймауту, быстрая проверка доступности воркера, отдельный пул потоков.

**R3 (P2, код). Лимит ленивых загрузок не считает загрузку зависимостей версий.** В счёт идут только новые пакеты и `go.mod`; обращения к источнику за зависимостями конкретных версий (PyPI JSON, документ версии npm, цепочки POM) не считаются, а резолверы с перебором пробуют много версий. Обещание «не больше 500 обращений» выполняется не полностью. В Go наоборот: считаются и документы, уже лежащие в БД (`go/resolver.py:104-106`).

**R4 (P2, гипотеза). Тяжёлые участки резолверов NuGet и crates идут в цикле событий.** Обход NuGet до 50 тыс. шагов без уступки управления останавливает весь API на время расчёта: процесс uvicorn один (`nuget/resolver.py:152-175`). Резолвер crates копирует состояние на каждом шаге. *Что сделать:* периодически уступать управление или считать в пуле потоков, как PyPI.

**R5 (P2, код). Клиент Redis для кэша resolve создаётся на каждый запрос и не закрывается** (`resolver/cache.py:27-29`). Под нагрузкой растёт число соединений. Одинаковые одновременные запросы считаются каждый отдельно: общей блокировки на ключ нет.

**R6 (P2, код). Кэш resolve для RPM не знает о ревизии repodata.** Ответ считается по снимку воркера, а действительность кэша проверяется по `synced_at` пакетов каталога; обновление repodata не сбрасывает ответ до часа. Параметры источника (`arch`, `releasever`) не входят в отпечаток профиля.

**R7 (P2, код). PyPI молча теряет часть требований.** Требование, которое не разбирает `packaging` (старые спецификаторы вроде `>=1.0-1`), пропускается без предупреждения (`pypi/connector.py:284`); `foo @ https://…` превращается в обычный поиск `foo` в индексе; `requires_dist: null` сохраняется как «зависимостей нет», а не «неизвестно». *Что сделать:* сохранять такие требования с пометкой и предупреждением, как это сделано для git- и file-зависимостей npm.

**R8 (P2, код). Ограничения экосистем, о которых ответ не предупреждает.** Сводка — в таблице ниже. Общий принцип исправления: всё, что резолвер пропустил или приблизил, должно попадать в `warnings` или `errors` узла.

**R9 (P3, код). Мало эталонов там, где больше всего использования.** У PyPI два эталонных проекта (оба про колёса torch), у npm три. Extras, маркеры, yanked, пререлизы, конфликты peer-зависимостей и алиасы проверены только unit-тестами, без сравнения с pip и npm. *Что сделать:* добавить по пять эталонов.

**R10 (P3, код). Расхождения опций со спекой.** `environment.go_version` не влияет на подрезку графа, только даёт предупреждение; флага MSRV для crates, обещанного в §9.1, нет; `max_rounds` принимается и не используется; NuGet при превышении внутреннего лимита обхода (50 тыс.) сообщает о лимите узлов (2 000) и сам лимит узлов не проверяет (`nuget/resolver.py:157-158`).

**R11 (P3, код). Дублирование в адаптерах и резолверах.** Цикл GET с повторами скопирован в восьми файлах, тело ETag-детектора — в шести, обвязка резолвера (`_Aborted`, `_check`, тройной `except`) — в семи. HTTP-клиент создаётся на каждый запрос без переиспользования соединений; размер ответа не ограничен; `Retry-After` не учитывается. *Что сделать:* общий `get_with_retry` в `services/http.py` с пулом и пределом размера, базовый ETag-детектор.

**R12 (P3, код). rpm-worker: память и целостность.** Файлы repodata скачиваются и распаковываются в память без предела (`repo.py:142`, `modules.py:57-62`); каждый resolve строит свой пул libsolv по всем источникам, кэш пулов вытесняет по порядку добавления; подпись `repomd.xml` не проверяется, целостность держится на TLS и контрольных суммах. Тестов на несовпадение контрольной суммы, параллельную синхронизацию и вытеснение кэша нет.

### Ограничения по экосистемам

| Экосистема | Не поддержано или приближено | Предупреждение в ответе |
|---|---|---|
| PyPI | sdist без метаданных; совместимость колёс проверяется только по платформе, без тега Python, ABI и архитектуры; маркеры `platform_release`, `platform_version` берутся с сервера API; прямые URL-требования | нет |
| npm | `overrides`, `resolutions`, lock-файлы в пакетах; `include_optional` не действует; при конфликте peer нет повтора, как у npm; dist-tag как ограничение корня отклоняется | git, file, url — да; остальное — нет |
| crates | MSRV; зависимости с `registry=`; нераспознанный `cfg(...)` считается не подходящим ни одной платформе | `registry` — да; `cfg` — нет |
| Go | `replace` и `exclude` только из окружения; `retract` помечает версии, но MVS их не избегает; директива toolchain | только несовпадение `go_version` |
| NuGet | только `net5.0+` и `netstandard` (решение Q7); платформенные TFM (`net8.0-windows`); `PrivateAssets` и `ExcludeAssets`; центральное управление версиями | только если нет ни одной подходящей группы |
| Maven | профили активируются только по `<jdk>` и `activeByDefault`; зависимости с `${…}` в координатах пропускаются; проблемы загрузки parent и BOM остаются в `raw_metadata.problems`; квалификаторы `-dev`, `-ea`, `-preview` считаются стабильными и могут стать «последней версией» | частично |
| RPM | четыре архитектуры; нет проверки подписи; нет исключений и базового состояния системы; при недоступном источнике ответ считается по старому снимку | про старый снимок — нет |

## 9. Эксплуатация, CI, тесты, документация

### Эксплуатация и поставка

**O1 (P1, код). В репозитории нет production-окружения.** Единственный compose-файл запускает frontend через `npm run dev`, образ ставит зависимости через `npm install` мимо lock-файла, адрес API зашит как `http://localhost:8000` (`frontend/Dockerfile`, `docker-compose.yml:101-111`): с другой машины интерфейс обращается к её собственному localhost. Node 20 в образе снят с поддержки с апреля 2026. *Что сделать:* многоэтапная сборка (`npm ci`, `vite build`, nginx или caddy с проксированием `/api`), относительный адрес API, отдельный `docker-compose.prod.yml` без публикации портов БД и Redis.

**O2 (P1, код). Образы и контейнеры собраны для разработки.** Нет `USER` ни в одном Dockerfile, нет `.dockerignore`; образ API несёт тесты с 23 МБ фикстур, `build-essential`, pytest и ruff. У `worker`, `beat`, `rpm-worker` и `frontend` нет проверок здоровья и лимитов памяти; в `docker-compose.stand.yml` у `rpm-worker` нет `restart: unless-stopped`, то есть после перезагрузки машины RPM-задачи на стенде перестанут обслуживаться. В контейнере rpm-worker два процесса Celery, смерть фонового незаметна. API — один процесс uvicorn без `--proxy-headers`.

**O3 (P1, стенд). Бэкапы не ротируются, не сжимаются и не проверяются.** `db_backup.sh` пишет несжатый текстовый дамп при каждой миграции и `stand.sh up`; сейчас три файла на 1,2 ГБ, последний — 927 МБ. Копий вне машины нет, они лежат на том же диске, что и том БД. Оборванный дамп остаётся на диске под обычным именем. *Что сделать:* сжатие или `--format=custom`, запись во временный файл с переименованием, хранить N последних, проверка `pg_restore --list`.

**O4 (P1, код). Восстановление небезопасно.** `db_restore.sh` льёт дамп с `--clean` в работающую базу, не останавливая `api`, `worker` и `beat`, перед этим не делает страховочную копию и перезапускает только `api` и `worker`, скрывая ошибку перезапуска (`|| true`). Учебного восстановления в CI нет. *Что сделать:* остановка сервисов, страховочный дамп, проверка ревизии и счётчиков после; сценарий учения на изолированном проекте, как в `check_migrations.sh`.

**O5 (P1, код). Порты и учётные данные по умолчанию.** Postgres, Redis и API публикуются на всех интерфейсах (`"5432:5432"`, `"6379:6379"`), пароль БД по умолчанию совпадает с именем, Redis без пароля и без постоянного хранения, admin-токен имеет известное dev-значение. Проверка дефолтов при старте не смотрит на пароль БД и срабатывает только при `APP_ENV=production`. *Что сделать:* привязать порты к `127.0.0.1` в базовом compose, расширить проверку.

**O6 (P2, код). Beat — единая точка, пропущенное расписание не догоняется.** Если beat не работал в 03:00 UTC (например, во время `stand.sh migrate`), ежедневное обновление пропускается до завтра; файл расписания и очередь Redis не переживают пересоздание контейнера. *Что сделать:* при старте проверять по журналу `runs`, что последний прогон не старше 26 часов; том для Redis с `appendonly`.

**O7 (P2, код). `/health` не проверяет зависимости.** Отвечает `ok` без обращения к Postgres и Redis; проверка здоровья compose проходит при лежащей базе. *Что сделать:* `/health/ready` с `SELECT 1` и `PING`.

**O8 (P2, код). Нет правил алертов и идентификатора запроса.** Метрики есть, файла правил, дашбордов и конфигурации сбора нет; лог текстовый, без идентификатора запроса и без трассировки; нет метрик пула БД, длины очередей и падений задач Celery. *Что сделать:* `docs/alerts.rules.yml` с тремя алертами из чек-листа (после #81 и #83), идентификатор запроса в логах и в `trace_id` ответа.

**O9 (P2, код, #89). Настройки из `.env` не доходят до контейнеров.** Плюс 15 настроек из `config.py` не описаны ни в одном примере (`SOURCE_BREAKER_*`, `CRATES_API_*`, `RELEASE_DATES_*`, `DAILY_UPDATE_STALE_RETRY_SECONDS` и др.), а `API_HOST` и `API_PORT` ни на что не влияют.
