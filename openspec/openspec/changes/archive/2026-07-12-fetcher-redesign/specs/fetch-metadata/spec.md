# fetch-metadata: контуры получения метаданных пакета

## ADDED Requirements

### Requirement: Demand-driven контуры синхронизации
Фетчер SHALL поддерживать пять контуров получения метаданных: seed (стартовый список с рекурсивным дозаполнением зависимостей), lazy fetch (по факту обращения через API/резолвер/админ), batch refresh (периодическое обновление oldest-N по `synced_at`), retry (повторная обработка транзиентных ошибок из очереди `sync_failures`), enumeration (полная индексация реестров с листингом).

#### Scenario: Lazy fetch неизвестного пакета
- **WHEN** запрошен пакет, отсутствующий в БД
- **THEN** фетчер загружает его метаданные из реестра, сохраняет и возвращает пакет в рамках того же запроса

#### Scenario: Batch refresh по расписанию
- **WHEN** наступает интервал batch refresh
- **THEN** обновляются N пакетов с самым старым `synced_at`, и `synced_at` каждого успешно обновлённого пакета сдвигается

### Requirement: Фоновая работа per-registry
Все фоновые контуры SHALL планироваться и исполняться per-registry: каждый реестр имеет собственные расписание, курсор и состояние синхронизации (`SyncState`), признак включённости (`sync_enabled`) и приоритет (`sync_priority`). Добавление или перенастройка реестра (URL, auth, расписание) MUST NOT требовать деплоя кода — только изменения строки `registry` через admin API.

#### Scenario: Добавление PyTorch index
- **WHEN** администратор регистрирует реестр `pytorch` (ecosystem `pypi`, протокол `pypi-simple`) через admin API
- **THEN** фоновые контуры начинают обслуживать его по собственному расписанию без перезапуска и деплоя, а его состояние sync отслеживается отдельно от pypi.org

#### Scenario: Отключение реестра
- **WHEN** у реестра установлен `sync_enabled = false`
- **THEN** фоновые контуры пропускают его, а уже сохранённые данные остаются доступными в каталоге

### Requirement: Полная индексация реестров с листингом (enumeration)
Для реестров с `enumerate_enabled = true` фетчер SHALL периодически перечислять полный список имён пакетов реестра (для `pypi-simple` — корень simple index; для внутренних npm — каталожный API) и ставить отсутствующие в БД пакеты в очередь синхронизации батчами с сохранением курсора. Enumeration MUST NOT перезагружать уже известные пакеты — только обнаруживать новые имена.

#### Scenario: Индексация внутреннего hosted-репозитория
- **WHEN** зарегистрирован внутренний Nexus pypi-hosted с `enumerate_enabled = true`, содержащий 300 пакетов
- **THEN** после цикла enumeration все 300 пакетов присутствуют в каталоге и находятся поиском

#### Scenario: Прерывание enumeration
- **WHEN** цикл enumeration прерван на середине списка
- **THEN** следующий цикл продолжает с сохранённого курсора, не начиная сначала

### Requirement: Идентичность пакета при нескольких реестрах
Пакет SHALL быть один на `(ecosystem, namespace, normalized_name)` независимо от числа реестров; присутствие в каждом реестре SHALL фиксироваться связкой пакет↔реестр. Версии пакета SHALL быть объединением версий по всем реестрам; каждый артефакт SHALL хранить реестр происхождения. Метаданные пакета (description, license, авторы) SHALL синхронизироваться из primary-реестра; данные из реестра с более бедным протоколом MUST NOT затирать поля, полученные из более богатого источника.

#### Scenario: Версии из двух реестров одной экосистемы
- **WHEN** `torch` присутствует на pypi.org (версия `2.1.0`) и в PyTorch index (версия `2.1.0+cu121`)
- **THEN** в каталоге один пакет `torch` с обеими версиями, артефакты каждой версии указывают на свой реестр

#### Scenario: Пакет только во внутреннем реестре
- **WHEN** пакет существует только во внутреннем hosted-реестре с протоколом `pypi-simple`
- **THEN** пакет присутствует в каталоге и поиске с тем объёмом метаданных, который отдаёт протокол, и внутренний реестр является его primary

### Requirement: Фиксация коллизий имён между реестрами
Если имя пакета обнаружено одновременно во внутреннем (hosted) и публичном реестре, фетчер SHALL зафиксировать флаг коллизии на связке пакет↔реестр. Если артефакты с одинаковыми `version + filename` из разных реестров имеют разные checksums, фетчер SHALL зафиксировать флаг расхождения. Фетчер MUST NOT предпринимать блокирующих действий — только фиксация фактов.

#### Scenario: Внутреннее имя появилось в публичном реестре
- **WHEN** пакет, известный из внутреннего hosted-реестра, обнаруживается на pypi.org
- **THEN** на связках пакет↔реестр появляется флаг коллизии, доступный API и UI

### Requirement: Полнота данных за один sync пакета
За один sync пакета фетчер SHALL сохранить: метаданные пакета, все версии со статусами, артефакты-метаданные каждой версии (filename, URL, размеры, checksums), уязвимости, авторов, dist-tags и зависимости latest-версии. Зависимости исторических версий SHALL гидратироваться лениво при первом обращении (дерево/resolve) с фиксацией признака гидратации.

#### Scenario: Гидратация исторической версии
- **WHEN** запрошено дерево зависимостей версии, у которой признак гидратации не установлен
- **THEN** фетчер догружает зависимости этой версии из реестра, сохраняет их и устанавливает признак гидратации

### Requirement: Идемпотентный upsert метаданных
Повторный sync пакета SHALL быть идемпотентным: пакет и версии обновляются по естественным ключам (`ecosystem + normalized_name`, `package_id + version`), зависимости и артефакты версии заменяются атомарно per version. Повторный sync без изменений в реестре MUST NOT приводить к дублям строк.

#### Scenario: Конкурентный lazy fetch одного пакета
- **WHEN** два запроса одновременно инициируют lazy fetch одного пакета
- **THEN** в БД возникает ровно один пакет без дублей версий, оба запроса получают результат

### Requirement: Выбор latest-версии по правилам версионирования экосистемы
Определение latest-версии SHALL использовать семантику версий экосистемы (для PyPI — `packaging.Version`); лексикографическое сравнение строк версий MUST NOT применяться.

#### Scenario: Fallback при отсутствии версии в манифесте
- **WHEN** манифест не содержит явного поля latest и доступны версии «9.0» и «10.0»
- **THEN** latest определяется как «10.0»

### Requirement: Экономное хранение сырых ответов реестра
В `raw_metadata` пакета фетчер SHALL сохранять только компактные разделы ответа реестра (для PyPI — `info` и `urls`); пер-версионные массивы (`releases`) SHALL раскладываться по строкам версий и MUST NOT дублироваться в блобе пакета.

#### Scenario: Sync популярного пакета с сотнями релизов
- **WHEN** синхронизируется пакет, у которого массив `releases` составляет большую часть ответа
- **THEN** `raw_metadata` пакета не содержит `releases`, а данные файлов каждой версии доступны в строке соответствующей версии

### Requirement: Расширяемость контракта коннектора
Контракт коннектора SHALL позволять добавить новый протокол (ближайший — `npm`; запланированы `maven2`, `goproxy`, `go-git` для внутренних Go-модулей в git) реализацией методов коннектора и нормализаторов без изменения контуров синхронизации, pipeline записи и retry-политики. Отсутствие классификатора для экосистемы MUST NOT блокировать её каталог: probe-контракт экосистемы определяется отдельно, метаданные работают без него.

#### Scenario: Добавление npm-коннектора
- **WHEN** добавляется реализация коннектора npm
- **THEN** контуры seed/lazy/refresh/retry/enumeration работают для npm-пакетов без изменений в своём коде

#### Scenario: Экосистема без классификатора
- **WHEN** подключён maven-реестр, для которого классификатор не разработан
- **THEN** каталог, поиск и версии maven-пакетов работают полностью, отсутствует только слой классификации
