# Proposal: Классификация в каталожном API, курация, экспорт

## Why

Слой классификации (classification-layer) пишет вердикты в БД, но каталог их не отдаёт: веб-интерфейсу нечего показывать, кураторам негде править пометки, LLM-слою нечем питаться. Это замыкает вторую ключевую задачу продукта на пользователя.

## What Changes

- Карточка пакета отдаёт блок классификации latest-версии: статус, роли (с evidence/provisional), машинные свойства (с evidence), эффективные свойства, ручные пометки, связи (plugin-of/platform-payload), реестры присутствия с флагами коллизий.
- Правило эффективных свойств (инвариант classifire №4): машинные − снятые кураторами (present=false) + добавленные (present=true); пометка конкретной версии побеждает пометку «все версии»; применяется во всех точках чтения (карточка, фильтры, stats, экспорт).
- Фильтры списка пакетов: `role`, `status`, `cap_all`, `cap_none` (по эффективным свойствам), в дополнение к существующим.
- `/stats` дополняется блоком классификации: total/by_status, счётчики ролей и эффективных свойств.
- Курация: `POST /api/v1/annotate` (upsert пометки) и `POST /api/v1/annotate/delete` — под admin-токеном (в classifire auth не было); валидация ecosystem/capability/существования пакета.
- Экспорт/перенос: CLI `export-annotations` / `import-annotations [--replace]` (annotations.jsonl — канал переноса датасета classifire) и `export-llm-input` (llm_input.jsonl: не-ok вердикты + описания версий, вход L2).

## Capabilities

### Modified Capabilities

- `classification`: добавляются требования выдачи в API, эффективных свойств, курации и экспорта.

## Impact

- Код: `classifier/effective.py`, схемы/эндпоинты packages + system + annotate, CLI-команды экспорта/импорта.
- Не затрагивается: фетчер, правила классификатора, resolver, UI (следующий этап).
