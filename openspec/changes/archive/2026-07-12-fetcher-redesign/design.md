# Design: Единый фетчер

## Context

Два существующих фетчера:

- **classifire** (`classifire/fetch.py`, stdlib, SQLite): батчевый pull пакетов без снапшота; глубина — манифест + скачивание дистрибутива + probe (entry_points.txt, top_level.txt, состав файлов, bin-скрипты, tarball-README); одна версия на пакет (latest/pinned); снапшоты immutable; auth per registry из INI с защитой `headers_for`; ошибка — строка в `package.last_fetch_error`, повтор раз в сутки.
- **PackageHub** (`backend/app/connectors|fetcher|tasks`, httpx + Celery, PostgreSQL): demand-driven контуры (recursive seed, lazy fetch, batch refresh по `synced_at`, retry-очередь `sync_failures`); ширина — все версии, зависимости (гидратация latest сразу, исторические лениво), артефакты-метаданные, уязвимости, авторы, dist-tags, Level-1 resolve; retry-таксономия с backoff+jitter; auth к upstream отсутствует; внутрь дистрибутива не заглядывает.

Целевая система — веб-интерфейс к прокси-репозиторию: каталог + резолвер (нужна ширина) и классификатор (нужна глубина probe). Весь исходящий трафик должен уметь ходить через прокси.

Мультирепозиторная реальность (модель данных PackageHub её уже предусматривает — Registry first-class, PackageRegistry m2m, SyncState per registry, `Artifact.registry_id`):

- у одной экосистемы несколько реестров: pypi.org и PyTorch index (`download.pytorch.org/whl` — только PEP 503 simple, без JSON API, версии с local labels `2.1.0+cu121`);
- внутренние корпоративные репозитории npm/PyPI (Nexus, Verdaccio, Artifactory): hosted-пакеты, которых нет в публичных реестрах, и прокси-зеркала публичных;
- целевое состояние — система знает обо **всех** артефактах всех подключённых реестров и даёт единый поиск.

Ограничения: PostgreSQL/Redis/Celery уже в стеке; опубликованные версии в реестрах неизменяемы; артефакты в PackageHub пересоздаются при каждом sync (`_replace_artifacts` = delete + insert).

## Goals / Non-Goals

**Goals:**

- Один фетчер, закрывающий обе оси: все версии пакета (каталог/резолвер) и probe дистрибутива (классификатор).
- Probe как независимый контур: его сбой или отставание не влияет на sync метаданных.
- Реестры, auth и прокси — конфигурация в данных (`registry`), одинаковая для метаданных и артефактов.
- Несколько реестров одной экосистемы: добавление реестра (PyTorch index, внутренний Nexus) — операция администратора, не деплой.
- Полная индексация реестров, поддерживающих листинг (внутренние репозитории), — система знает обо всех их артефактах.
- Единая retry-модель для всех контуров, включая probe.
- Контракт коннектора, в который npm ложится без изменения ядра.

**Non-Goals:**

- Реализация npm-коннектора (отдельный чейндж; контракт обязан его выдерживать).
- Классификатор и его триггеры (потребитель probe; отдельный чейндж).
- Полная синхронизация реестров по change feed (остаётся demand-driven модель MVP).
- Изменения резолвера, каталожного API, UI.
- Миграция исторических данных из SQLite classifire (отдельный чейндж вместе с аннотациями).

## Decisions

### D1. Каркас — PackageHub, probe — отдельный контур

Контуры: `seed`, `lazy fetch`, `batch refresh`, `retry`, **`probe`**, **`enumeration`** (D13). Probe — отдельная Celery-очередь со своим лимитом параллелизма.

Почему не «probe внутри sync-пайплайна»: другой профиль нагрузки (мегабайты бинарника против килобайт JSON), другой ритм (одна версия, а не все), другая политика ошибок («нет wheel» — валидный результат, а не сбой sync). Альтернатива «отдельный сервис-пробер» отвергнута: та же кодовая база нормализаторов и моделей, лишняя инфраструктура.

### D2. Что пробится: версия dist-tag `latest` по умолчанию, любая версия по запросу

После успешного sync пакета ставится probe-задача для версии, на которую указывает `latest`. Для произвольной версии probe запрашивается явно (API/классификатор/куратор). При смене `latest` новая версия пробится, старые результаты остаются (история).

Почему не «все версии»: трафик и хранилище растут на порядок без потребителя; классификатор classifire всегда работал по одной версии — семантика сохраняется.

### D3. Результат probe — immutable-строка на дистрибутив версии

У версии может быть несколько дистрибутивов (PyPI: sdist + wheels под платформы; Maven: jar + sources + javadoc; npm: один tgz). Таблица `dist_probe(id, version_id FK → package_version, registry_slug, artifact_filename, is_representative boolean, fetched_at, entry_points_txt, top_level_txt, file_facts jsonb, readme_extracted boolean, error text, UNIQUE(version_id, artifact_filename))`.

По умолчанию пробится **один представительный** дистрибутив версии (выбор — D4), строка получает `is_representative = true`; классификатор читает представительную строку. Probe других дистрибутивов той же версии (платформенный wheel — важно для будущей роли binary-payload) — по явному запросу, дополнительными строками. Есть строка для пары (версия, файл) — не перекачиваем (published-дистрибутивы неизменяемы). `error` — тоже результат: «all wheels exceed size limit» хранится и виден классификатору как сигнал `needs-data`. Принудительный re-probe — только явное удаление строки (админ-операция).

Почему не FK на `artifact`: `_replace_artifacts` пересоздаёт строки артефактов при каждом refresh — FK умирал бы вместе с ними. Артефакт идентифицируется парой `registry_slug + artifact_filename`.

README из дистрибутива кладётся не в `dist_probe`, а в слой описаний (таблица описаний целевой схемы, origin `tarball-readme`) — как в classifire; `readme_extracted` — флаг факта.

### D4. Выбор артефакта для probe — эвристика classifire дословно

PyPI: только `bdist_wheel` ≤ `probe_max_wheel_bytes` (default 20 МБ); предпочтение `none-any`, затем лексикографически; фиксировать `platform_wheel` в `file_facts`. Нет пригодного wheel — permanent-результат с error (sdist не распаковываем в v1 — совпадает с поведением classifire). npm (контракт на будущее): tarball ≤ `probe_max_tarball_bytes` (default 30 МБ по `unpackedSize`), факты `has_index_js`, ext_counts, README по regex.

Извлекаемые факты: `entry_points.txt`, `top_level.txt` (сырым текстом — парсинг остаётся классификатору), `file_facts` (total, ext_counts top-15, scripts из `.data/scripts/`, platform_wheel), README (лимит 500 000 символов).

### D5. Реестры как данные: `registry.auth_config` + инвариант `headers_for`

Источник адресов и auth — таблица `registry` (`base_url`, `api_url`, `auth_config` jsonb: `{"type": "bearer"|"basic", ...}`, значения шифруются на уровне приложения). Env-переменные (`SYNC_PYPI_JSON_BASE_URL` и пр.) остаются bootstrap-override'ом при первом создании registry-строки, дальше истина — БД.

Инвариант (из classifire): авторизационный заголовок отправляется **только** на хост из `base_url`/`api_url`; редирект скачивания артефакта на другой хост (CDN) — заголовок не передаётся. Реализация: сравнение netloc до каждого запроса; httpx redirect с заголовками отключён, редиректы обрабатываются вручную.

Прокси-режим: адрес прокси-репозитория подставляется как `base_url`/`api_url` реестра — фетчер не различает «прямой реестр» и «прокси», это свойство конфигурации.

### D6. Транспорт: клиент на процесс, семафоры, rate limit

Один `httpx.AsyncClient` на процесс (воркер Celery / API) с connection pool limits вместо клиента на запрос (текущий PackageHub). Параллелизм probe — семафор (default 8, наследие `workers` classifire). `get_rate_limit()` коннектора перестаёт быть декоративным: обёртка-троттлер выдерживает минимальный интервал между запросами к одному registry (для npm/crates пригодится сразу).

### D7. Таксономия ошибок: retryable / not-found / artifact-unusable

- **retryable** (SSL, таймауты, connect/read/write, 429, 5xx): backoff + jitter внутри задачи; исчерпание попыток → `sync_failures`, авторетрай beat'ом. Как в PackageHub, без изменений.
- **not-found** (404): типизированный `PackageNotFound`, не ретраится, не в `sync_failures`. 401/403 — отдельный класс `RegistryAuthError` (не «not found», как схлопывает classifire): попадает в лог и метрику, сигнал о протухшем токене.
- **artifact-unusable** (новый, только probe): bad zip/tar, превышение лимита, нет пригодного артефакта. Permanent: пишется в `dist_probe.error` как результат, не ретраится, не в `sync_failures`.

### D8. Дедупликация конкурентных загрузок — Redis-лок для probe

`_in_flight`-словарь lazy fetcher'а защищает только внутри процесса; для метаданных этого достаточно (upsert идемпотентен, дубль — лишний GET на килобайты). Для probe дубль — лишние 20 МБ: Redis-лок `probe:{version_id}` с TTL ~120 с; проигравший лок не ждёт, а завершает задачу (строка появится у победителя); `INSERT ... ON CONFLICT DO NOTHING` — последняя линия.

### D9. Экономия хранения: `releases` не хранится в raw_metadata пакета

Правило classifire: из PyPI-ответа в `package.raw_metadata` сохраняются `info` + `urls`; массив `releases` раскладывается по `package_version.raw_metadata` и в пакетном блобе не дублируется. Для npm — versioned endpoint / abbreviated packument вместо полного.

### D10. Все контуры работают per-registry

Единица планирования фоновой работы — реестр, не экосистема. Beat итерирует строки `registry` с `sync_enabled = true`; у каждого реестра свои расписание, курсор (`SyncState.cursor_data`), приоритет (`sync_priority`) и метрики. Lazy fetch при промахе опрашивает реестры экосистемы в порядке приоритета. Добавление PyTorch index или внутреннего Nexus — `POST /admin/registries` + строка конфигурации; код не меняется, пока протокол поддержан.

Почему не per-ecosystem с списком зеркал внутри коннектора: реестры одной экосистемы различаются протоколом, auth, ритмом обновления и политикой (внутренний hosted нужно индексировать целиком, pypi.org — нет); это свойства строки данных, а не ветвления в коде.

### D11. Протокол коннектора — отдельное измерение от экосистемы

Новое поле `registry.protocol`; коннектор выбирается по нему, а не по экосистеме:

- `pypi-json` — JSON API pypi.org (полные метаданные за один запрос);
- `pypi-simple` — PEP 503/691 simple index + PEP 658 metadata: PyTorch index, внутренние Nexus/Artifactory/devpi (и hosted, и proxy);
- `npm` — протокол npm registry: npmjs.org, Verdaccio, Nexus npm говорят на одном диалекте (versioned endpoint + packument).

Запланированные протоколы (контракт коннектора обязан их выдерживать, реализация — отдельные чейнджи): `maven2` (layout Maven-репозитория: Central, Nexus maven hosted; метаданные из POM), `goproxy` (протокол Go module proxy), `go-git` (внутренние Go-модули: репозиторий — это git, не Nexus; список версий — git-теги, зависимости — go.mod из тега). Классификатор для maven/go не разработан — это не блокирует каталог: probe-контракт этих экосистем определяется вместе с их классификатором, фетчер метаданных от него не зависит.

Все протоколы выдают один нормализованный выход (`NormalizedPackage`). Протоколы неравны по полноте: `pypi-simple` не отдаёт description/license/authors — коннектор заполняет то, что есть (имена, версии, файлы, hashes, requires-python, yanked; при PEP 658 — и зависимости), остальное берётся из primary-реестра пакета (D12). Недостающие поля MUST NOT затирать уже известные из более богатого источника.

### D12. Идентичность пакета: один Package, версии — объединение, артефакты помнят реестр

`Package` остаётся уникальным per `(ecosystem, namespace, normalized_name)` — глобально для всех реестров; присутствие в реестрах — `PackageRegistry` (m2m). Версии пакета — объединение по всем реестрам: `torch 2.1.0` с pypi.org и `torch 2.1.0+cu121` из PyTorch index — разные строки `package_version`; каждый артефакт несёт `registry_id`. Метаданные пакета (description, license, authors) синхронизируются только из primary-реестра (`is_primary`); выбор primary: реестр с самым богатым протоколом, при равенстве — наивысший `sync_priority`.

Коллизии имён: если пакет обнаружен и во внутреннем hosted-реестре, и в публичном — это событие фиксируется флагом на связке `PackageRegistry` (сигнал dependency confusion / shadowing, витальный для веб-интерфейса прокси). Если одинаковые `version + filename` в двух реестрах имеют разные checksums — второй флаг (подмена артефакта). Фетчер только фиксирует факты; политика реагирования — вне scope.

### D13. Контур enumeration: полная индексация реестров с листингом

Шестой контур. Для реестров с `enumerate_enabled = true` периодическая задача перечисляет полный список имён пакетов и ставит недостающие в очередь sync (батчами, с курсором в `SyncState`). Источники листинга: `pypi-simple` — корневая страница simple index (полный список проектов одним запросом); `npm` (Verdaccio/Nexus) — их каталожные/поисковые API. Дефолты: внутренние реестры — `enumerate_enabled = true` (система обязана знать всё их содержимое), публичные гиганты (pypi.org, npmjs.org) — `false`, для них остаётся demand-driven модель; PyTorch index (~десятки пакетов, тысячи версий) — `true`.

Почему не «полная синхронизация всех реестров»: для публичных это full crawl из полной SPEC (вне scope MVP), а для внутренних объём мал и полнота обязательна — граница проходит по флагу реестра, не по коду.

Из Nexus подключаются **только hosted**-репозитории (решение зафиксировано): proxy-части не регистрируются (публичный оригинал уже подключён напрямую или через прокси-репозиторий), group-URL не регистрируются (смешанный листинг hosted+proxy сделал бы enumeration неотличимым от full crawl публичного зеркала).

### D14. Мелкие исправления, фиксируемые контрактом

- Fallback выбора latest-версии — через `packaging.Version`, не лексикографический sort (`_pick_latest_version` в текущем коннекторе даёт «9.0» > «10.0»).
- Lazy fetch различает not-found / upstream-error в возвращаемом типе (сейчас оба схлопываются в `None`), чтобы fail-fast `/resolve` и будущий probe-контур получали причину.

## Risks / Trade-offs

- [Probe добавляет бинарный трафик и распаковку в воркеры] → лимиты размеров, семафор, probe только для `latest` по умолчанию, весь трафик через кеш прокси-репозитория.
- [Распаковка недоверенных архивов (zip-bomb, path traversal)] → чтение только в память из `BytesIO` без записи на диск (как в classifire), жёсткий лимит размера до распаковки, извлечение только известных имён файлов; никогда не `extractall`.
- [`dist_probe.error` как permanent может «залипнуть» после починки внешней причины (поднят лимит, появился wheel)] → повторный probe при смене `latest` происходит естественно (новая версия); для той же версии — админ-операция re-probe.
- [Шифрование `auth_config` на уровне приложения — ключ в env] → осознанный MVP-компромисс; ротация ключа — операционная процедура, вне scope.
- [Redis-лок с TTL не строгая гарантия] → допустимо: худший случай — двойное скачивание, консистентность держит PK + ON CONFLICT.
- [Заморозка fetch classifire до готовности npm-коннектора оставляет npm-часть датасета без обновлений] → приемлемо: снапшоты immutable, датасет не портится, только не пополняется; npm-коннектор — следующий чейндж.
- [`pypi-simple`-реестры дают бедные метаданные — пакеты только из внутреннего hosted останутся без description/license] → честно показывать полноту источника в карточке; для внутренних hosted это ожидаемо (метаданные из самого пакета добёт probe + классификатор).
- [Слияние версий по имени пакета из разных реестров может склеить чужие пакеты (dependency confusion)] → фетчер не решает, а фиксирует: флаг коллизии имён internal↔public и флаг расхождения checksums на одинаковых filename; отображение — задача UI, политика — вне scope.
- [Enumeration большого внутреннего прокси-зеркала (Nexus proxy на pypi.org) может внести сотни тысяч имён] → enumeration ставит в очередь sync только недостающие имена и работает батчами с курсором; для прокси-зеркал публичных реестров enumeration по умолчанию выключен — индексируется hosted-часть.

## Migration Plan

1. Миграция схемы: `dist_probe`, использование `registry.auth_config` (колонка уже есть в модели данных).
2. Транспортный слой: общий клиент, троттлер, `headers_for`; регресс — существующие интеграционные тесты sync.
3. Probe-контур: Celery-очередь, задача, эвристика выбора артефакта, извлечение фактов (порт из `classifire/fetch.py`, поведение 1:1).
4. Подключение к контурам: enqueue probe после sync latest; admin-endpoint probe конкретной версии.
5. Заморозка `classifire/fetch.py` (README-пометка): источником новых данных становится единый фетчер.

Rollback: probe-контур изолирован — отключение очереди возвращает систему к текущему поведению PackageHub; `dist_probe` аддитивна, метаданные от неё не зависят.

## Open Questions

- Нужен ли probe sdist-фолбэк для PyPI-пакетов без wheel (~несколько % датасета): в v1 — нет (паритет с classifire), решить по доле `error = "no wheel available"` в реальном датасете.
- Хранить ли сырой архивный листинг (полный список файлов) сверх `ext_counts` — полезно будущему LLM-слою, но раздувает `file_facts`; предложение: top-level листинг до N=200 имён.
- Событие от прокси-репозитория (access log → enqueue lazy fetch) — формат интеграции определяется, когда прокси зафиксирует свой интерфейс; контракт фетчера от этого не зависит (enqueue по имени пакета уже есть).
- Автоопределение `protocol` при регистрации реестра (probe корневых эндпоинтов) или всегда явное указание администратором — предложение: явно, с кнопкой «test connection».
- `go-git`: механика enumeration внутренних Go-модулей (откуда брать список git-репозиториев: статический конфиг или API группы GitLab/Gitea) — решить при проектировании go-коннектора вместе с его классификатором.
