# Design: on-demand-classification

## Context

Прокси-репозиторий строит систему проверок; классификатор — один из её источников. Контракт интеграции: проверка вызывает PackageHub синхронно и получает факты; решение о допуске принимает сама. Внутри PackageHub весь конвейер (fetch → probe → classify) уже существует как корутины, но связан через Celery — для внешнего синхронного вызова нужен inline-путь.

## Goals / Non-Goals

**Goals:** синхронный сервис фактов по (ecosystem, name) с гарантией «факты по latest есть в ответе или явная ошибка»; только факты, никаких вердиктов. **Non-Goals:** пер-версионная классификация; ре-классификация по событиям; изменение фоновых контуров; формат callback/webhook для прокси (интеграция pull-моделью).

## Decisions

### D1. Inline-оркестрация, не Celery

Эндпоинт выполняет недостающие шаги в API-процессе: lazy fetch (существующий типизированный результат) → probe latest (вызов той же корутины, что у Celery-задачи: Redis-лок и идемпотентность защищают от гонки с воркером) → classify (офлайн, миллисекунды). Celery-путь остаётся для фонового наполнения; inline-путь — для гарантии ответа проверке без зависимости от воркера. Весь вызов под общим таймаутом (`facts_timeout_seconds`, default 30) → 504 при превышении.

### D2. Fail-fast семантика (как у /resolve)

not_found upstream → 404; auth-ошибка реестра → 502 с причиной; retryable upstream-сбой → 503 без partial-ответа (ретраи — забота вызывающего). Probe-«unusable» (нет wheel, битый архив) — НЕ ошибка: это факт, классификация выполняется по probe_failed-веткам правил, ответ 200.

### D3. Только факты — контрактно

Ответ: идентичность (ecosystem/name/namespace/latest), жизненный цикл из живых строк каталога (deprecated, статус версии), блок классификации (status/status_reason, facets с evidence, machine+effective capabilities, annotations, relations), реестры присутствия с флагами коллизий, метки времени (synced_at/classified_at/classifier_version). Поля вида allow/deny/decision/score запрещены требованием спеки — граница ответственности между каталогом фактов и системой проверок.

### D4. Политика охвата — latest (зафиксировано решением)

Автоматическая и по-требованию классификация работают по версии dist-tag latest. `refresh=true` пересинхронизирует метаданные перед выдачей (сдвиг latest, deprecated) — после чего probe/classify новой latest выполняются в том же вызове.

## Risks / Trade-offs

- [Inline probe в API-процессе — скачивание артефакта до N МБ в цикле запроса] → лимиты probe уже стоят; таймаут вызова; для горячего пути ответ обычно из готовых данных (<50ms), холодный путь редкий по определению demand-driven модели.
- [Гонка inline-пути с Celery-воркером] → Redis-лок probe + идемпотентные вставки уже это закрывают; при проигранном локе inline-путь ждёт и перечитывает результат.

## Open Questions — блок «режим обновления» (сознательно не решён)

Зафиксировано пользователем 2026-07-13: конечного решения нет, требуется проработка отдельным чейнджем.

- **Ре-классификация при изменении жизненного цикла** (пакет стал deprecated/yanked после классификации): вероятное решение — офлайн re-classify по событию refresh, но событие/триггер не спроектированы.
- **Пер-версионная классификация**: кандидаты-политики — новые версии при refresh, версии из resolve/access-log прокси, кураторский `--all-versions`; для pypi нужен ленивый пер-версионный манифест. Не решено, что включать по умолчанию.
- **UI**: вероятный вариант — привязать блок классификации к селектору версий (модель deps.dev: зона пакета + зона версии), сейчас блок прибит к latest. Ждёт решения по двум пунктам выше.
