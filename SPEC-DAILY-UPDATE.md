# PackageHub — Ежедневное обновление каталога и журнал событий

> Раз в сутки для каждой экосистемы находим пакеты каталога, изменившиеся в источниках, перечитываем только их и записываем, что именно изменилось. На журнале событий строится дайджест «что обновилось за день / неделю».

**Версия:** 1.0
**Дата:** 2026-11-07
**Статус:** реализовано для 7 экосистем (pypi, npm, maven, nuget, go, crates, rpm).
**История:** 0.2-draft → 1.0: переписано под код этапов E0–E6. Исходный черновик (только PyPI) остался в истории git.

Общий дизайн мультиэкосистемного каталога: [SPEC-MULTI-ECOSYSTEM.md](./SPEC-MULTI-ECOSYSTEM.md). Источники — §6, ежедневное обновление — §8. Здесь описано поведение, как оно реализовано.

## 1. Задача и рамки

Ежедневное обновление:

- берёт только пакеты, которые уже есть в каталоге;
- спрашивает у каждого включённого источника, что изменилось, его собственным детектором (§3);
- перечитывает изменившиеся пакеты через общий pipeline из всех их источников и сливает результат;
- пишет события изменений (§4) и запись о прогоне в журнал `runs` (§2).

Чего оно не делает:

- не зеркалирует источники целиком: новые пакеты в каталог не попадают;
- не скачивает артефакты (wheel, sdist, jar): хранятся только описания файлов.

Новые источники для уже известных пакетов ищет отдельная еженедельная задача, presence probe (SPEC-MULTI-ECOSYSTEM §6.6). Она запускается по воскресеньям в 04:00 UTC (`presence_probe_enabled`, `presence_probe_day_of_week`, `presence_probe_hour_utc`). Ежедневный прогон следит только за источниками, в которых пакет уже известен.

## 2. Прогон

### 2.1 Расписание и запуск

Celery beat (`backend/app/celery_app.py`), задача `app.tasks.daily_update.run_daily_update`. Настройки (`backend/app/config.py`):

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `daily_update_enabled` | `true` | добавлять ли задачу в расписание beat |
| `daily_update_hour_utc` | `3` | час запуска, UTC |
| `daily_update_minute_utc` | `0` | минута запуска |
| `daily_update_concurrency` | `4` | сколько пакетов перечитывается параллельно |
| `daily_update_stale_retry_seconds` | `300` | пауза перед повтором устаревших ответов (§2.3) |

Ручной запуск:

- `POST /api/v1/admin/daily-update` без тела: ставит задачу в очередь для всех экосистем (SPEC-MVP-API §5.5);
- `python -m app.cli daily-update [--ecosystem <e>]`: выполняет прогон в текущем процессе, для всех экосистем или одной;
- `scripts/stand.sh daily-update`: то же, что CLI, в контейнере стенда.

### 2.2 Один прогон на экосистему

Задача обходит экосистемы в порядке enum `Ecosystem`. Берутся те, у которых есть плагин и хотя бы один включённый источник. Каждая экосистема получает свой прогон и свою запись в `runs`.

Шаги прогона одной экосистемы:

1. **Охрана от наложения.** Если для той же пары операция + экосистема уже есть запись `running` моложе 6 часов, новый прогон не стартует и возвращает `status: "skipped"` с `running_run_id`. Запись старше 6 часов считается брошенной и не мешает.
2. **Обнаружение.** Для каждого включённого источника вызывается его `ChangeDetector` с курсором из `sync_states.cursor_data` (§3). Детектор возвращает изменившиеся пакеты с новой ревизией, пропавшие из источника и новый курсор.
3. **Деградировавшие источники пропускаются.** Источник за открытым предохранителем (circuit breaker) в обнаружении не участвует: в `per_registry` у него `status: "degraded"`. Предохранитель открывается после `source_breaker_failures` (5) ошибок запросов подряд на `source_breaker_cooldown_seconds` (600). Любой ответ источника, в том числе «нет такого пакета», закрывает его. Пакеты такого источника перечитываются позже, когда он вернётся.
4. **Сбой одного детектора** не останавливает остальные: в `per_registry` у источника `status: "failed"` и текст ошибки. Курсор такого источника не сдвигается.
5. **Перечитывание.** Пакет, изменившийся хотя бы в одном источнике, перечитывается из всех своих источников (SPEC-MULTI-ECOSYSTEM §8.1), параллельно в пределах `daily_update_concurrency`. Pipeline сам пишет события (§4).
6. **Закрытие прогона.** Счётчики, `per_registry`, `events_by_kind`, статус. Курсоры сохраняются, если прогон не `failed`.

Прогон идемпотентен: повторный запуск находит только то, что не обновилось в первый раз.

### 2.3 Устаревшие ответы и ожидающие пакеты

PyPI JSON и packument npm отдаются через CDN и могут отставать от ленты изменений. Поэтому ревизия, которую вернул источник при перечитывании, сравнивается с объявленной детектором:

- числовые ревизии (serial PyPI) сравниваются по значению: ответ старше объявленного — устарел;
- ревизия вида `not:<ревизия>` (лента знает только «пакет изменился») устарела, пока ответ равен старой ревизии.

Устаревшие пакеты перечитываются один раз через `daily_update_stale_retry_seconds`. Если и после повтора ответ устарел, пакет попадает в `pending` курсора тех источников, что его объявили. Следующий прогон перечитает его ещё раз. Если пакет устарел и после этого, он остаётся до еженедельной полной сверки.

### 2.4 Недоступные пакеты

- Источник сообщил, что пакета нет (`missing`): пакет перечитывается из всех своих источников. Если он пропал из всех, `packages.unavailable_at = now()`, пакет получает событие `project_unavailable`, а у его строк `package_registries` ставится `missing_since`.
- Исчезновение из одного источника из нескольких отмечается только в `package_registries.missing_since` и события не даёт.
- Пакет, который вернулся, получает `project_restored`, `unavailable_at` обнуляется.

### 2.5 Статус и журнал

| Статус | Когда |
|---|---|
| `running` | прогон идёт |
| `success` | ни один пакет не завершился ошибкой, все источники отработали (`per_registry.*.status = ok`) |
| `partial` | есть пакеты с ошибкой, либо источник деградировал или сбойнул |
| `failed` | прогон прервало необработанное исключение; в `error` его класс и текст |

Ошибка одного пакета не валит прогон: она записывается в `sync_failures` (операция `daily_update`) и повторяется задачей `retry-failed-sync`.

Журнал — таблица `runs` (`backend/app/models/run.py`), общая для всех операций (daily update, seed, presence probe, retry). Ключевые колонки:

| Колонка | Смысл |
|---|---|
| `operation` | `daily_update` |
| `ecosystem` | экосистема прогона |
| `status` | см. выше |
| `started_at`, `finished_at` | время |
| `packages_total`, `packages_checked` | различные пакеты каталога по включённым источникам экосистемы |
| `packages_changed` | сколько пакетов пошло на перечитывание |
| `packages_updated`, `packages_failed`, `packages_unavailable` | итоги перечитывания |
| `events_created` | сколько событий записано |
| `per_registry` | по слагу источника: `status` (`ok` / `failed` / `degraded`), `tracked`, `changed`, `missing`, `cursor` или `error` |
| `events_by_kind` | счётчики событий по видам |
| `error` | текст при `failed` |

Курсоры детекторов хранятся отдельно: `sync_states.cursor_data` по источнику. Там же состояние предохранителя (`degraded_until`).

Ревизия, известная нам по пакету и источнику, лежит в `package_registries.upstream_revision` (и `etag`). Колонки `packages.last_serial` в схеме нет.

## 3. Детекторы по экосистемам

Детектор — часть адаптера источника (`adapter.change_detector()`, протокол `ChangeDetector` в `backend/app/ecosystems/base.py`). Результат — `ChangeSet`: `changed` (пакет и новая ревизия), `missing`, `cursor`, `reconcile_all`.

Ленточные детекторы (npm, Go, NuGet) при потерянной ленте и раз в 7 дней выполняют полную сверку детектором-«сверщиком». Если сверщика нет, выставляется `reconcile_all`: все пакеты источника перечитываются.

| Экосистема, источник | Откуда узнаём об изменениях | Курсор | Запасной вариант |
|---|---|---|---|
| pypi, `pypi-warehouse` | корневой Simple-индекс, `_last-serial` каждого проекта (`pypi/changes.py`); пакет изменился, если serial новее сохранённого или проект вернулся | `index_serial` | `/simple/{name}/` по каждому пакету, если корневой индекс недоступен |
| pypi, `pypi-simple` | условный GET страницы проекта по ETag | нет | нет |
| npm, источник с `changes_url` (npmjs) | лента репликации `_changes`: страницы по 10 000 до `update_seq` на начало прогона, фильтр по именам каталога (`npm/changes.py`) | `last_seq`, `reconciled_at` | потеря или сброс ленты, первый прогон и раз в 7 дней: условный GET packument каждого пакета по ETag |
| npm, прочие | условный GET packument по ETag | нет | нет |
| nuget, источник с `catalog_url` (nuget.org) | каталог: страницы новее курсора, записи `PackageDetails` и `PackageDelete`, фильтр по id без учёта регистра (`nuget/changes.py`) | `commit`: `commitTimeStamp` последнего прочитанного коммита, `reconciled_at` | первый прогон и раз в 7 дней: условный GET registration index каждого пакета по ETag |
| nuget, прочие | условный GET registration index по ETag | нет | нет |
| go, источник с `index_url` (proxy.golang.org) | `index.golang.org`: версии, впервые отданные прокси с курсора, страницы по 2000, фильтр по путям модулей (`go/changes.py`) | `since`: время последней записи, `reconciled_at` | первый прогон, отказ индекса и раз в 7 дней: `@v/list` каждого модуля; у модулей без тегов учитываются и псевдо-версии |
| go, прочие | полный GET `@v/list` каждого модуля; ревизия — хэш списка | нет | нет |
| crates, `cargo-sparse` | условный GET файла индекса крейта по ETag | нет | нет |
| maven, `maven2` | `maven-metadata.xml` каждого GA в каждом источнике, где он есть: условный GET, пока ревизия — ETag; иначе полный GET и сравнение `lastUpdated` или хэша | нет | нет |
| rpm, `rpm-repodata` | один вызов rpm-worker на источник: условно обновляет `repomd.xml`, при смене ревизии разбирает `primary` и `modules.yaml` и сравнивает сборки пакетов каталога с сохранённой ревизией (EVR) | `revisions` по пакетам, `config` — хэш настроек источника | неизменный репозиторий пропускается, кроме первого прогона и смены настроек источника (base_url, arch, доступ) |

Общие правила:

- Без ленты (crates, maven, `pypi-simple`, прочие источники npm, NuGet и Go) детектор опрашивает каждый пакет каталога. Запросы идут параллельно в пределах `daily_update_concurrency`. Читаются все пакеты, поэтому стоимость растёт с размером каталога.
- Пакет без известной ревизии детекторы по ETag считают изменившимся.
- Ошибка проверки одного пакета не роняет источник: пакет считается неизменившимся до следующего прогона.
- Пакет, уже известный как недоступный, повторно не сообщается, пока не вернётся.

Снимок замеров (2026-10-27, PyPI): корневой индекс ≈10 МБ (gzip), меньше секунды, 924 578 проектов; за ≈22 часа из 5 707 пакетов каталога изменились 143. Стоимость остальных детекторов — SPEC-MULTI-ECOSYSTEM §8.1.

## 4. События

Событие рождается из сравнения снимка пакета **до** и **после** записи в pipeline (`backend/app/fetcher/events.py`, `diff_package`), а не из внешнего источника. Поэтому события одинаковы для любого пути загрузки: daily update, ленивая загрузка, ручная загрузка, seed. Они пишутся в той же транзакции, что и метаданные.

Журнал — таблица `package_events`: `package_id`, `version`, `kind`, `detected_at`, `occurred_at`, `run_id`, `details` (jsonb). Срок хранения не ограничен.

Пакета не было в БД: пишется только `tracking_started`, событий по историческим версиям нет.

### 4.1 Виды событий

Enum `PackageEventKind` (`backend/app/models/enums.py`), 12 видов.

| Вид | Когда пишется | `details` |
|---|---|---|
| `tracking_started` | пакет впервые попал в каталог | `latest_version` |
| `release_added` | версия впервые появилась в любом источнике | `previous_version`, `bump`, `prerelease`; `modules` для модульной сборки RPM; `backfill: true` для версий, пришедших с новым источником |
| `release_yanked` | версия стала yanked; также когда новая версия появилась сразу yanked (кроме backfill) | `reason` |
| `release_unyanked` | yank снят | пусто |
| `release_removed` | версия пропала из всех источников или лишилась файлов | пусто |
| `release_restored` | версия со статусом `removed` вернулась | пусто |
| `release_deprecated` | у версии появилась deprecation (npm, NuGet) | сама deprecation: причины, сообщение, замена |
| `vulnerability_added` | в `vulnerabilities` пакета новая запись | `id`, `aliases`, `summary` (первая строка, до 300 символов), `fixed_in` |
| `vulnerability_withdrawn` | у известной уязвимости появилось `withdrawn_at` | `id` |
| `project_unavailable` | пакет пропал из всех своих источников (§2.4) | пусто |
| `project_restored` | недоступный пакет вернулся | пусто |
| `source_added` | у пакета появился новый источник, либо известная версия появилась ещё в одном источнике | `registry` (слаг); во втором случае заполнено и поле `version` |

`occurred_at`: у `release_added` — дата релиза версии, у уязвимостей — `published_at` или `withdrawn_at`, у остальных `null`. Для них точность — до суток (`detected_at`).

Часть видов бывает не у всех экосистем: у Maven нет `release_removed` (релизы не удаляются), у RPM его заменяет статус `superseded` без события.

### 4.2 Статусы версий

Enum `PackageVersionStatus`: `active`, `yanked`, `deprecated`, `unlisted`, `removed`, `superseded`. Строки версий не удаляются: на них ссылаются зависимости и журнал. Версия, пропавшая из всех источников, получает `removed`; у RPM — `superseded`.

Событие пишется при смене статуса версии в целом, а не в одном источнике: статус в источнике хранится в `version_sources`.

### 4.3 `bump`, `previous_version`, backfill

Правило действует с миграции `20261106_0014`, которая пересчитала и старые события.

- Новая версия сравнивается с ближайшей **меньшей** из известных, а не с предыдущей по порядку обхода: бэкпорт (7.30.2 рядом с 8.12.4) не становится опорой текущей линии.
- `previous_version` — эта ближайшая меньшая версия, стабильная или нет. Если меньших нет, берётся `latest_version` из снимка до записи.
- `bump` (`major`, `minor`, `patch`, `pre`, `other`) считает схема версий экосистемы относительно ближайшей меньшей **стабильной** версии. Пример: 3.1.1 → 3.2.0rc1 → 3.2.0 даёт `pre`, затем `minor`.
- Несколько новых версий за один fetch обрабатываются по возрастанию, каждая учитывается следующими.
- `backfill: true` получает версия, которую публикуют только новые для пакета источники: для нас это новость, а не релиз. Дайджест такие события игнорирует. Версия, пришедшая так сразу yanked, события `release_yanked` не получает.
- Новый источник пакета даёт одно событие `source_added` на пакет, а не по событию на каждую его версию.
