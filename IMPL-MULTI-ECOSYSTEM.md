## 0. Правила процесса

1. **Ветка и draft PR на этап с первого коммита.** Ветки `claude/me-e0a-schema`, `claude/me-e0b-pipeline`, `claude/me-e0c-api`, `claude/me-e05-pypi-indexes`, `claude/me-e1-npm` и т. д. Draft PR открывается сразу, чтобы CI проверял каждый коммит WP (§5, P0.9). В ready-for-review PR переводится после ревью этапа, сразу с auto-merge (merge commit), без отдельного подтверждения. Слияние — через обязательные проверки CI.
   Этапы идут подряд без ручного запуска: WP, проверки, ревью этапа, auto-merge, стенд, следующий этап. Работа останавливается только на вопросе владельцу (п. 2), на сбое, который не удаётся исправить, или в конце плана. Падения CI, конфликты и комментарии ревью в PR этапа будят сессию через монитор PR в приложении.
2. **Расхождение → вопрос.** Если при реализации спека расходится с кодом, данными или поведением источника, WP останавливается, вопрос уходит владельцу продукта с вариантами и рекомендацией. Независимые WP продолжаются. Решение записывается в спеку тем же PR.
3. **Делегирование Sonnet.** Механические задачи: перенос без изменения поведения, Pydantic-схемы, маршруты по образцу, фикстуры, тесты по списку случаев, Dockerfile, CLI. Opus делает контракты, алгоритмы (merge, резолверы, детекторы с курсорами, модульность RPM), миграции данных и ревью. Задание Sonnet — по шаблону (P0.11): файлы, образец, запреты, критерий готовности, команда проверки. Результат Sonnet Opus проверяет до коммита.
4. **Защищённые пути.** `backend/app/ecosystems/base.py` (контракт), `backend/alembic/versions/`, `design/` меняет только Opus. Исполнитель-Sonnet о них предупреждён в определении агента, ревьюер проверяет diff.
5. **Ревью субагентом.** На завершении этапа (каждого из трёх PR E0 и каждого следующего этапа) субагент-ревьюер проверяет diff против спеки и плана. Найденное исправляется до перевода PR в ready, отчёт кладётся в описание PR. WP с пометкой «ревью» (миграции, алгоритмы) проверяются сразу после готовности.
6. **Проверка на стенде** в конце каждого PR: перед миграцией бэкап (`stand.sh backup`), миграция при остановленных worker и beat, seed, ежедневное обновление, дайджест, resolve.
7. **Совместимость.** Старые маршруты API и формат resolve живут как алиасы, пока UI не переедет на новые (конец E7). Затем удаляются отдельным PR. Видимое изменение поведения в E0 одно — удаление batch refresh (R3).

## 2. Миграции: expand → переключение кода → contract

0006 только **добавляет** и **копирует**. Колонки, которые потом удаляются, теряют NOT NULL или получают DEFAULT, чтобы новый код мог писать без них. NOT NULL на новых колонках ставится в 0007, когда весь код пишет их сам.

|---|---|---|---|

| `packages.origin` | Добавить с `DEFAULT 'dependency'`, заполнить по T12 | Пишет origin | — |
| `packages.deprecated/_message/_alternative` | `deprecation jsonb` add+copy | Читает и пишет `deprecation` | Удалить старые |

**Повторное заполнение в 0007.** Код до E0-B не пишет новые колонки, а старые меняет. Поэтому строки, **появившиеся или изменённые** между 0006 и E0-B, расходятся с производными колонками. 0007 сначала снова вызывает `backfill()` из 0006 (загружает модуль 0006 по пути) для пустых строк. Затем досинхронизирует расхождения:
- `dependencies_state = 'hydrated'`, где `features.dependencies_hydrated = true`, а состояние ещё `pending`;
- `engines` из `requires_python`, где они различаются;
- `package_registries.upstream_revision` из `packages.last_serial`, где `upstream_revision IS DISTINCT FROM last_serial::text`;
- `runs` из `update_runs` через `ON CONFLICT DO UPDATE` (прогон мог быть `running` в момент 0006).

Только после этого ставятся NOT NULL и делается VALIDATE.

**Механика.**
- Три фазы:
  1. **Быстрый DDL** в одной транзакции под `lock_timeout = 5s`: колонки без перезаписи таблиц, пустые новые таблицы.
  2. **`backfill()`** в `autocommit_block`. Пакеты по 5000 строк, выборка по возрастанию первичного ключа (keyset), один оператор на пакет. Каждая строка `package_versions` переписывается один раз.
  3. **Индексы** `CREATE INDEX CONCURRENTLY` после данных. Невалидный индекс от прерванного прогона удаляется. Уникальные ограничения подключаются через `USING INDEX`, FK создаются `NOT VALID`.
- **Возобновление.** Каждый шаг выбирает только незаполненные строки. При падении в фазе 2 или 3 `alembic_version` остаётся 0005 при уже применённом DDL фазы 1. Выход — повторить upgrade (DDL идемпотентен); downgrade в этом состоянии не делать.
- Миграция не импортирует код `app`: кодировщик `sort_key` и нормализация вкопированы, чтобы историческая миграция не менялась вместе с кодом.
- Downgrade 0006 удаляет только добавленное.
- 0007 объявлена **необратимой**, бэкап перед ней обязателен (`stand.sh migrate` его делает и останавливает worker и beat, P0.10).

**Проверка.**
- `scripts/check_migrations.sh` (в CI):
  - синтетический каталог 0005 → head → проверки `check_head.sql` (все преобразования, порядок PEP 440, T13, нормализация только PyPI, индексы валидны) → `alembic check`;
  - downgrade: схема совпадает со схемой 0005 с точностью до разрешённых остатков;
  - негативный случай T16: миграция останавливается, `alembic_version` не меняется.
- На копии стенда: счётчики до и после, у всех версий `sort_key` и `version_sources`. Приложение старой версии на схеме после 0006: seed, интеграционные тесты, smoke.
- После 0007: сценарии `design/schema-check` во временной БД из дампа (slug сценариев отличаются от существующих).
